# 데스크톱 앱 지침 (desktop/)

desktop/(Electron 앱)과 tests/checkDesktop*.js를 고칠 때 적용한다. 공통 규칙(CLI 계약·로그 줄 형식·코드 스타일·검증 명령)은 [루트 CLAUDE.md](../CLAUDE.md)를 따른다. 사용자 관점의 화면 동작은 [README.md](README.md)에 있고, 아래는 코드를 고칠 때 지켜야 할 규칙이다.

## 엔진 연동

- 엔진 코드를 import하지 않는다. 앱 exe를 ELECTRON_RUN_AS_NODE=1로 실행해 엔진 스크립트를 자식 프로세스로 띄운다(개발 중에는 저장소의 autopilot/core/, 패키지에서는 resources/engine/core/). CLI 계약(인자·stdout 로그 줄 형식·exit code·stop)이 UI와의 인터페이스다.
- 엔진 로그 줄을 해석하는 곳은 셋이다. 로그 줄 형식을 바꾸면 모두 고치고 해당 검증으로 확인한다.
    - 러너: autopilotRunner.cjs의 파서 → tests/checkDesktopRunner.js
    - 지난 실행: runHistory.cjs(autopilotRunner.parseLine·isReplay를 그대로 쓴다) → tests/checkDesktopHistory.js
    - 화면: viewFormat.js(applyStoryEntry·buildTranscript·describePastRun) → tests/checkDesktopView.js
- 신규 개발 로그: 러너 파서는 헤더 `Mode : 신규 개발 (…)`을 state.mode("build", 유지 보수는 "")로, `[단계] <이름> 시작|완료|확인 대기|실패`(과 `- 개발로 되돌림 (N/M)`)를 state.step(`{phase: plan|design|build|qa|security, status: running|done|awaiting|failed, qaRetries, securityRetries}`, 없으면 null. 되돌린 횟수는 되돌림 줄의 단계(테스트/QA·보안검토)로 키를 정해 따로 세고 다음 단계 줄에도 이어 둔다)로 읽는다. 단계 이름은 러너의 PHASE_LABELS(엔진 config.js와 같다)로 키를 찾고 들여 쓴 줄은 읽지 않는다. `[단계] <이름> 건너뜀`은 러너가 읽지 않고(단계 카드는 컴포저의 skip으로 그린다) viewFormat.describeStepLine이 한 문장으로만 바꾼다. 지난 실행 요약에는 mode가 담긴다. 화면은 viewFormat.describeStepLine이 단계 줄을 한 문장으로 바꿔 이야기(시각 없는 문장)와 지난 실행 대화(kind notice)에 넣고, 종료 사유 `<단계> 확인 대기`·`신규 개발: 모든 단계 완료`·`테스트/QA 실패`·`보안검토 실패`는 FINISH_REASONS·PAST_STATUSES(확인 대기는 사유 그대로 warn, 단계 실패도 warn)·describeFinish 제목("확인을 기다리고 있어요.", "<단계>에서 멈췄어요.")으로 들려준다. 단계 실패(viewFormat의 PHASE_FAILED_PATTERN)는 엔진이 종료 코드 0으로 끝내지만 getRunPhase가 정상 종료 대신 `<단계>에서 멈춤`(warn)으로 보여 상태 줄과 태그가 같은 말을 한다.
- 재연결: 앱을 닫았다 켠 사이에도 엔진이 살아 있어 열린 탭의 프로젝트에서 실행 중이면, 앱을 켤 때(보는 프로젝트)와 창에 포커스가 올 때(모든 탭) 엔진의 status로 확인해 연결한다. 연결하면 로그 파일을 처음부터 읽어 상태를 복원하고(이때 읽은 회차는 시각을 알 수 없다) 1초마다 새 로그와 pid 생존을 확인한다. 종료 신호는 stop, 모델 변경은 set, 강제 종료는 pid로 하며, 종료 코드는 알 수 없어 사유는 로그의 종료 줄에서 읽는다. 연결한 엔진은 앱 소유가 아니므로 창을 닫아도 종료하지 않는다.
- 로그는 메인 프로세스가 최근 3000줄만 보관한다.

## 프로젝트 세션

- 실행은 프로젝트마다 세션 하나(러너·시작 중·재연결 확인 중·직전 상태·앱 소유 여부)를 갖는다. sessionPool.cjs(Electron에 의존하지 않는 순수 모듈, tests/checkDesktopSessions.js가 검증)가 getProjectKey 기준으로 보관하므로 경로 표기(대소문자·슬래시·junction)가 달라도 같은 프로젝트는 세션 하나다. 세션을 만드는 곳은 autopilotIpc.cjs의 createSession이다.
- 프로젝트를 다루는 IPC(start·stop·kill·set-options·reset-settings·update-settings·reset-progress·get-phase·approve-phase·open-report·지난 실행 목록/읽기/열기/삭제·용량·정리·get-state)는 `projectDir`을 받는다(start·set-options·update-settings는 요청 객체 안, 나머지는 마지막 인자). 생략하면 활성 프로젝트(settings.json의 projectDir)다. 렌더러가 보낸 경로는 sessionPool.get이 이미 열린 프로젝트인지 확인하고, 아니면 INVALID_PROJECT로 거부한다(열린 적 없는 경로를 지우거나 읽는 일을 막는다).
- 집계: 계정 추가·제거·로그인·데이터 폴더 변경 잠금(accounts의 isRunning)과 설정 가져오기·기본값 복원 거부는 어느 세션이든 실행 중이면 적용하고, 설정 덮어쓰기(update-settings·reset-settings)·계정 선택·프로젝트 바꾸기는 그 프로젝트가 실행 중일 때만 거부하며(화면의 잠금은 보는 탭 기준이고, 모든 탭에 걸친 일은 hooks/useAnyRunning이 다른 탭까지 본다), 종료 확인·트레이 숨김(confirmClose·isOwnedEngineRunning)은 앱이 시작한 세션 전체를 본다. 절전 방지·작업표시줄 진행률·트레이 툴팁은 실행 중인 모든 세션을 모아 판단한다(systemIntegration의 sessionStates. 진행률은 종료 시각이 있는 세션들의 평균 경과, 모두 대기 중이면 대기, 트레이는 하나면 단계·여럿이면 개수). 알림은 프로젝트마다 직전 상태와 비교하고, 탭이 둘 이상이면 본문 앞에 프로젝트 이름을 붙인다. 끝난 뒤 PC 동작은 다른 세션이 아직 실행 중이면(hasOtherActive) 하지 않고 마지막으로 스스로 끝나는 실행이 정한다. 창에 포커스가 오면 열린 모든 탭의 프로젝트에서 계속 실행 중인 엔진에 연결한다(attachRunningEngines).
- 이벤트: autopilot:state는 `{ projectDir, state }`, autopilot:log는 `{ projectDir, entries }`로 보낸다(projectDir은 세션이 가진 경로 표기). 화면(ui/actions/events.js의 handleStateEvent·handleLogEvent)은 지금 보는 프로젝트(appStore의 settings.projectDir)의 이벤트만 반영한다. 그래서 활성 프로젝트는 항상 세션의 projectDir 문자열로 저장한다(handleSelectProject. 이미 열린 프로젝트를 다른 표기로 고르면 세션의 표기를 쓴다). 프로젝트를 고르면 응답에 새 세션의 state·logs를 담고 화면이 applySessionSnapshot으로 바꾼다. 응답 전에 나간 이벤트는 버려지지만 스냅샷에 담기고, 응답 뒤의 이벤트는 반영된다(메인 프로세스가 스냅샷을 만든 직후 동기적으로 응답한다). tests/tools/ui의 가짜 preload는 events.js가 없는 옛 화면에는 옛 형식으로 이벤트를 준다.
- 열린 탭은 전역 settings.json의 tabs(경로 배열, 열린 순서, 최대 MAX_TABS=8)이고 projectDir은 그중 활성 탭이다. normalizeSettings가 같은 프로젝트(getProjectKey가 같음)는 앞의 탭 하나만 남기고, 활성 프로젝트가 탭에 없으면 더하며, 활성 프로젝트의 표기는 탭에 저장된 것을 따른다(탭이 없는 옛 파일·낮은 버전 앱이 쓴 파일도 탭 하나로 열린다). 같은 프로젝트를 두 탭에서 열 수 없으므로 열려 하면 settingsStore.openTab이 새 탭 없이 원래 탭을 활성으로 하고 `existing: true`와 그 탭의 경로를 돌려준다. handleSelectProject는 openTab을 거쳐 지금 탭의 프로젝트를 바꾸고(replaceDir), 탭이 상한이면 TOO_MANY_TABS로 거부한다. sessionPool은 활성이거나 열린 탭인 프로젝트만 세션으로 받는다(getOpenDirs).
- 계정은 탭마다 고른다. 프로젝트 파일의 accountId가 우선하고 없으면 전역 accountId를 따른다(resolve가 settings.accountId에 합침). accountIpc는 getAccountId·setAccountId·resolveProjectDir·isProjectRunning을 받아 계정 선택(select-account)·계정 목록(get-accounts)·모델 목록(get-models)·시작(getRunAccount)이 프로젝트를 인자로 받는다(생략하면 활성 탭). 계정 선택은 그 탭이 실행 중일 때만, 계정 추가·제거·로그인·데이터 폴더 변경은 어느 탭이든 실행 중이면 거부한다. 새로 추가한 계정은 추가를 시작한 탭이 고른 계정이 된다. 프로젝트를 바꾸면 계정도 바뀔 수 있어 handleSelectProject가 계정 정보를 다시 보낸다. 지워진 계정을 고른 탭은 기본 계정으로 본다(getActiveId).
- 탭 IPC: open-tab(폴더를 골라 새 탭으로 열기, 이미 열린 프로젝트면 그 탭으로 이동)·activate-tab(projectDir)·close-tab(projectDir)은 select-project와 같은 결과(설정 보기·tabs·state·logs, 열었다면 existing)를 돌려주고(getSwitchResult), 닫기는 실행 중이거나 시작 중·엔진 연결 확인 중인 탭을 RUNNING으로 거부한다(isSessionBusy). 탭 요약은 getTabsPayload의 `{ active, tabs: [{ projectDir, name(폴더 이름), status, mode(build 또는 빈 문자열), step(지금 단계 plan·design… 또는 빈 문자열) }] }`이고 get-state·전환 결과에 담기며, 세션의 실행 상태(idle·running·stopping)가 바뀔 때만 autopilot:tabs로 보낸다(broadcastTabs. 상태 이벤트마다 설정을 읽지 않는다). select-project는 지금 탭의 프로젝트를 바꾸고 그 탭의 이전 세션을 버린다(대화상자 뒤에 isSessionBusy를 다시 확인해 RUNNING으로 거부한다). 세션을 버리는 곳은 sessionPool.close다.
- 설정은 settingsStore.resolve(projectDir)로 프로젝트를 지정해 읽는다(생략하면 활성 프로젝트). 이때 settings.projectDir은 지정한 프로젝트이고 remember도 그 프로젝트의 뷰를 돌려준다.

## 보안과 경로

- 렌더러에는 Node 권한을 주지 않는다. preload.cjs가 window.autopilot·window.appWindow만 노출한다.
- CSP가 inline style 속성을 막으므로 스크립트의 스타일은 style.setProperty로만 넣는다. React의 style prop은 CSSOM으로 적용돼 CSP에 걸리지 않는다(CSS 변수·anchorName 확인).
- 엔진이 알려준 경로는 믿지 않는다(projectFiles.cjs). 리포트 열기는 시작한 프로젝트의 .autopilot/progress/ 안의 report_*.html만 허용하고, 연결할 로그는 progress/ 안의 autopilot_*.log만 읽는다. 둘 다 링크를 실제 경로로 풀어 판단한다.
- 여러 AI 브레인스토밍 로그: `[브레인스토밍] <제공자> <단계> 안|검토 받는 중|받음|건너뜀: <이유>`는 러너가 state.brainstorm(`{provider, phaseLabel, kind: proposal|review, status: receiving|received|skipped, reason}`, 보내기를 허용하지 않았다는 줄은 status blocked, 없으면 null)으로 마지막 소식만 읽고, viewFormat.describeStepLine이 단계 줄처럼 한 문장으로 바꿔 이야기와 지난 실행 대화에 넣는다(describeBrainstormLine). 실행 화면 오른쪽 카드(run/RunCard의 BrainstormState, #card-ai)가 받는 중 · 받음 · 건너뜀(이유는 아래 줄)을 보인다. 받는 동안 1분마다 오는 `… 안|검토 진행 N분째 (최대 M분)[: <활동>]` 줄은 러너가 state.brainstorm에 elapsedMinutes · limitMinutes · activity를 더해 읽고(#card-ai-progress가 보임), describeStepLine은 이야기 · 지난 실행 대화에 넣지 않도록 빈 문자열을 돌려준다(러너와 viewFormat 모두 경과 줄을 상태 줄보다 먼저 판별해 활동 글이 상태 줄을 흉내 내지 못한다).
- Claude · Codex 협의 로그: `[협의] <단계> 시작 (최대 N번)`이 러너의 state.debate(`{phaseLabel, maxTurns, status: running|consensus|disputes|skipped, turns: [{provider, message, at(받은 시각 ms, 로그를 다시 읽은 발언은 0)}](최근 12마디), turnCount(받은 발언 수 전체. 주고받기 번호와 말풍선 key의 기준), disputes, reason}`)를 열고, `[협의] Claude|Codex: <발언>`이 turns에 쌓이며, `[협의] 합의했어요`·`[협의] 쟁점 N개를 남기고 끝냈어요`·`[협의] 건너뜀: <이유>`(시작 줄 없이도 온다)가 status를 정한다. `[단계] … 시작` 줄이 오면 state.debate를 비운다. 실행 화면은 status가 running인 동안 features/debate/DebateChat(#debate-chat, Claude 왼쪽 · Codex 오른쪽 카카오톡식 말풍선: 프로필 사진·이름, 말풍선 옆 시각(formatChatTime, 시각을 모르면 생략), 날짜가 바뀌는 곳의 날짜 구분선, 5줄을 넘는 긴 말은 흐리게 접고 `더 보기`로 펴며 글은 마크다운(굵게·코드·목록)으로 그린다. 엔진은 발언을 줄이지 않고(최대 300자) 한 줄로 펴서 쓴다에 이름과 프로필(components/ProviderAvatar: Claude는 마크, Codex는 >_ 를 브랜드 색 원에 넣은 것이라 색을 그 CSS의 변수로 둔다), 머리말의 참가자 아바타(말할 차례에 고리), 다음 차례의 빈 말풍선, 크기가 바뀌어도 맨 아래에 붙음)을 진행선 아래에 보이고 지난 문장(#story-past)을 숨긴다. viewFormat은 시작 · 끝 · 건너뜀 줄을 describeStepLine으로 한 문장으로 바꾸고(describeDebateLine), 발언 줄은 parseDebateTurn으로 읽어 이야기에는 누구 차례인지 한 문장(isDebate 항목을 바꿔 감)만, 지난 실행 대화(buildTranscript)에는 kind chat 말풍선으로 넣는다(ArchiveSheet의 chat-item debate).
- 협의한 단계의 승인: 엔진 status의 단계 상태에는 debate(`{phase, disputes: [{id, title, claude, codex}], resolved}`)가 있고 러너의 parseBuildPhase가 글자만 받아 길이를 묶어 읽는다(형식이 틀리면 단계 상태 전체를 버린다). 확인 기다림(approval/DebateReview)은 합의안(단계 산출물)과 협의 기록을 같은 크기의 탭 둘(.debate-tabs, 기록이 있을 때만)로 왼쪽에(협의 기록은 debate/DebateTranscript의 채팅방: 주고받기마다 구분선, 발언 아래 동의 · 반대 · 바꾼 점 칩), 시작 버튼과 쟁점마다 Claude 쪽 · Codex 쪽 라디오 카드를 오른쪽에 두고, 쟁점을 모두 고르기 전에는 시작 버튼을 잠근다. 시작은 actions/run의 approveAndStart(undefined, resolutions) → autopilot:approve-phase(projectDir, pick, resolutions)이고, 메인(getResolveArgs)이 아이디(d1~d99)와 쪽(claude·codex)·개수(10)를 검사해 `approve --resolve d1=claude,...`로 넘긴다. 쟁점이 없으면 --resolve 없이 승인한다.
- 신규 개발 산출물(autopilot:read-phase-doc·open-phase-doc, phase는 plan·design·qa·security와 브레인스토밍의 보조 안 `<plan|design>-<claude|codex>`(proposals/<단계>-<제공자>.md 또는 .html, 보조는 메인의 반대쪽 AI라서 메인이 Codex이면 Claude 안이다. 메인의 안은 단계 산출물 그 자체) · `<plan|design>-review-<claude|codex>`(proposals/<단계>-review-<검토자>.md) · 협의 기록 `<plan|design>-debate`(proposals/<단계>-debate.md, viewFormat.parseDebateTranscript가 말풍선으로 되읽는다(notes는 `{kind: agree|disagree|change, text}`, 시각은 알 수 없어 보이지 않는다)))은 렌더러가 단계 이름만 보내고 경로는 projectFiles의 PHASE_DOCS(docs/autopilot/plan.md·design.md·design/·qa.md·security.md)로만 정한다. 열린 프로젝트(sessionPool)만 받고, 실제 경로로 풀어 프로젝트 밖을 가리키는 링크·종류(파일·폴더)가 다른 것은 건너뛴다(getPhaseDoc). 읽기는 파일 앞 256KB(MAX_PHASE_DOC_BYTES, 경계에서 잘린 글자는 버린다)와 폴더의 이름 목록(링크 제외, 200개)뿐이고, 열기는 그 실제 경로를 shell.openPath로 연다. tests/checkDesktopRunner.js(checkPhaseDocs)가 검증한다.
- 시작 요청의 keepTasks가 참이면(단계 수정 요청) 작업을 다음 시작의 기본값으로 기억하지 않는다(launchRun의 remember).
- viewFormat.js는 DOM에 의존하지 않는 표시용 순수 함수(ES 모듈)이며 desktop/ui가 import하고 tests/checkDesktopView.js가 단독으로 불러 검증한다.

## 실행 설정과 허용 값

- 대상 프로젝트는 Git 저장소의 루트(.git이 있는 폴더)만 받는다(projectFiles.getProjectError). 고르기 전에는 시작 버튼이 잠기고 실행 중에는 바꿀 수 없다.
- .git이 없는 폴더를 고르면(select-project·open-tab, projectFiles.canInitGitRepo) 메인은 그 폴더와 하려던 일을 pendingGitInit에 기억하고 NOT_GIT_REPO(`data.projectDir`)로 답한다. 화면(actions/tabs.confirmGitInit)이 modal.confirm으로 묻고, 확인하면 autopilot:init-git-repo(인자 없음)가 기억한 폴더에만 main 저장소(`git init` 뒤 HEAD를 main으로, git 2.28 전도 됨)와 빈 첫 commit(`git commit --allow-empty -m init`, projectFiles.initGitRepo)을 만들고 하려던 일(프로젝트 바꾸기·새 탭)을 이어간다. 렌더러는 경로를 보내지 않고, 기억은 다음 대화상자나 한 번 쓰면 지운다. commit 작성자가 설정되지 않아 실패하면 지어내지 않고 git의 이유를 GIT_INIT_FAILED로 알린다(저장소는 만들어진 채 남는다). 유지 보수·신규 개발 모두 같은 흐름이다.
- 작업 모드와 신규 개발(덮어쓸 수 있는 키): mode(maintain·build, 기본 maintain), gates(plan·design의 부분 목록, 기본 둘 다), skip(design·qa·security의 부분 목록, 기본 없음. 엔진 `--skip`으로 넘기고, 건너뛰는 단계의 gates·brainstorm·designFormat·qaOnFail·securityOnFail은 engineArgs가 빼고 보낸다), allow(deps·large·external-api·send의 부분 목록, 기본 deps·large), designFormat(md·html·figma·image, 기본 html), qaOnFail·securityOnFail(테스트/QA·보안검토가 실패하면 개발로 되돌리는 횟수, 같은 형식 stop·retry:1~5, 기본 retry:3), mains(신규 개발에서 단계마다 그 단계의 회차를 돌리는 메인 AI, plan·design·build·qa·security의 부분 맵 claude|codex, 기본 {}는 모두 Claude이고 engineArgs.getMains가 빈 단계를 claude로 채운다)·brainstorm(메인의 반대쪽 AI가 보조로 따로 안을 낼 단계, plan·design의 부분 목록, 기본 없음)·debate(그중 협의로 돌릴 단계, plan·design의 부분 목록, 기본 없음, brainstorm에 없는 단계는 엔진 인자에서 빠진다)·crossReview(나란히 비교하는 단계의 서로 검토, 기본 false)·debateTurns(협의에서 주고받는 최대 횟수, 1~20의 정수, 기본 8, engineArgs.cjs의 DEBATE_DEFAULT_TURNS·DEBATE_TURNS_LIMIT가 원본이고 화면은 숫자 조절기(components/Stepper, ready/BuildReady의 AssistSettings)로 1~20을 정한다. 협의로 돌리는 단계가 있을 때만 `--debate-turns`로 넘기고 기본값과 같으면 생략한다. 어느 단계 칸에서 바꿔도 같은 값이고 협의를 꺼도 남음)·codexModel·codexEffort(Codex가 쓸 model·reasoning effort, 기본 빈 문자열은 Codex 설정을 따름, 엔진 config.js의 CODEX_MODEL_PATTERN·CODEX_EFFORT_LEVELS와 같은 값만 받고 engineArgs.cjs가 원본, 입력창의 Codex 알약에서 바꾸며 단계와 무관하게 늘 같은 값이고 Codex를 쓰지 않아도 남음). 단계 칸의 메인 선택(Claude·Codex)은 composer.setPhaseMain(phase, provider)로 mains를 바꾸고(기본 Claude는 맵에서 뺀다), 보조 선택(보조 없이 · 나란히 비교 · 협의)은 composer.setBrainstormMode(phase, none|compare|debate)로 brainstorm·debate를 함께 바꾼다(buildSteps.getBrainstormMode가 거꾸로 읽는다). 보조는 메인의 반대쪽 AI라서, Codex가 보조인 단계(메인이 Claude)는 프로젝트 내용이 Codex로 나가므로 allow에 send를 함께 켜고 Claude가 보조인 단계(메인이 Codex)는 send와 상관없다. 나란히 비교하는 단계가 없어지면 crossReview를 끈다. toggleAllow로 send를 끄면 Codex가 보조인 단계의 brainstorm·debate를 비우고(Claude 보조는 남긴다) 나란히 비교하는 단계가 없으면 crossReview도 끈다. getCliArgs는 기본(claude)이 아닌 단계만 `--main plan=codex,…`로 넘기고(신규 개발은 `--runner`를 보내지 않는다. 저장된 실행 에이전트가 새어 들지 않게), 보조를 쓸 수 있는 단계(engineArgs.getAssistedPhases: 보조는 메인의 반대쪽 AI이고 Codex 보조는 send가 있어야 하며 Claude 보조는 send와 상관없다)만 `--brainstorm`(협의 단계는 `<단계>:debate`)에 담고, Codex가 관여할 때(메인이 Codex이거나 보조가 Codex)만 값이 있는 `--codex-model`·`--codex-effort`를 붙이고 `--cross-review`는 나란히 비교하는 보조 단계가 있을 때만 붙인다. 옛 설정 파일에는 debate가 없어 기본값(협의 없음)이다. 값 목록은 engineArgs.cjs가 원본이고 엔진 config.js·ui/lib/constants.js와 같다. 컴포저(composerStore의 mode·gates·allow·designFormat·qaOnFail·securityOnFail, setMode·toggleGate·toggleAllow·setDesignFormat·setQaOnFail·setSecurityOnFail·getModeOptions. 목록은 고를 수 있는 값의 순서로 저장)가 시작·예약 저장 때 보내고, 메인은 pickModeOptions로 이 키만 받아(없으면 저장된 값) SETTING_VALIDATORS로 검사한다. getCliArgs는 build일 때만 `--mode build`와 `--gate`·`--allow`(비면 생략)·`--design-format`·`--qa-on-fail`·`--security-on-fail`(엔진 기본값과 같으면 생략)을 붙인다. build로 시작하면 launchRun이 엔진 status로 단계를 읽어(readBuildPhase) 모든 단계를 마쳤으면 BUILD_DONE, 기획(또는 돌려보낸 기획)인데 작업이 비면 TASKS_REQUIRED로 거부하고, 예약 시작은 확인을 기다리는 단계가 있으면 PHASE_AWAITING으로 건너뛴다(승인 없이 다시 하지 않는다). 지시개선의 작업 필수 검사는 build에서는 하지 않는다.
- 단계 상태: autopilot:get-phase(projectDir)가 엔진 status의 phase(`{phase, awaiting, qaRetries, securityRetries, proposals}`, 신규 개발을 한 적 없으면 null, 러너의 parseBuildPhase가 검증하고 securityRetries·proposals가 없는 옛 출력은 0·null로 읽으며 proposals 형식이 틀리면 전체를 null로 본다)를 돌려주고, autopilot:approve-phase(projectDir, pick)가 엔진 approve(`--pick claude|codex`, 그 밖의 값은 INVALID_PICK)를 실행한 뒤(실행 중이면 RUNNING) 새 상태를 돌려준다. autopilot:get-providers가 다른 AI 제공자를 쓸 수 있는지(`{codex: {available, reason, models}}`, claudeCli.getCodexStatus: PATH에 codex가 없으면 설치 안내, `codex login status`가 실패하면 로그인 안내, 1분 기억. 쓸 수 있으면 models(`[{id, label}]`)에 Codex가 `$CODEX_HOME` 또는 `~/.codex`의 models_cache.json에 캐시한 목록(visibility가 list, CODEX_MODEL_PATTERN을 통과한 것, 30개까지)을 담고 비공식 형식이라 읽지 못하면 빈 목록이다. 입력창의 Codex 알약(composer/AiPills, buildSteps.getCodexModelOptions)이 이 목록을 쓰고 저장된 모델이 목록에 없어도 그 값을 항목으로 보인다)를 알려주고 runsStore.providers(actions/runs.loadProviders, 시작 전 신규 개발 화면이 열릴 때와 AI 알약 팝오버를 열 때, Codex 알약은 처음에도 한 번. 결과가 codex 객체를 새로 만들므로 effect의 의존성에는 객체가 아니라 있는지 여부를 넣는다)에 둔다. 화면은 runsStore의 buildPhase에 두고 actions/runs.loadBuildPhase가 loadRecentRuns와 함께(앱 시작·탭 전환·실행 종료 뒤) 읽으며, actions/run.approvePhase가 승인하고 resetProgress 뒤에도 다시 읽는다.
- 종료 시각은 HH:mm 또는 날짜를 붙인 `yyyy-MM-dd HH:mm`(최대 engineArgs의 MAX_RUN_DAYS=7일 뒤)을 받는다. 시작할 때 engineArgs.getEndTimeError가 엔진과 같은 규칙(없는 날짜·지난 시각·7일 초과)으로 INVALID_END_TIME을 돌려준다. 날짜를 붙인 값은 다음 시작에 이미 지났을 수 있어 기억하지 않고(launchRun의 remember에서 뺀다), 저장하는 endTime은 HH:mm만이다(settingsStore의 END_TIME_PATTERN).
- 설정은 전역과 프로젝트로 나뉜다. 전역은 userData/settings.json 하나(선택한 프로젝트·계정·시스템 값과 모든 프로젝트의 기본값)이고, 프로젝트는 userData/project-settings/<폴더 이름>-<경로 해시 8자>.json(진행 기록과 같은 키 규칙)에 그 프로젝트가 덮어쓴 값만 둔다. 덮어쓸 수 있는 키(settingsStore의 OVERRIDABLE_KEYS)는 tasks·endTime·policy·extendOnLimit·extendLimitMinutes·commitPrefix·workBranch·logRetentionDays·model·modelVersions·effort·mode·gates·skip·allow·designFormat·qaOnFail이고, 프로젝트 파일에 없는 키는 전역 값을 따른다(키 단위 fallback). projectDir(활성 탭)·tabs(열린 탭 목록)·accounts·claudeDir·keepInTray·launchAtLogin은 전역에만 있다. 연결 저장소(LINKED_REPOS_KEY `linkedRepos`, 경로 배열, 작업 프로젝트를 빼고 engineArgs의 MAX_LINKED_REPOS=2개까지·중복 제외)는 프로젝트 파일에만 있고(OVERRIDABLE_KEYS 밖이라 설정 범위 줄·덮어쓴 키 목록에는 안 나온다) 계정처럼 이 PC에서만 뜻이 있어 내보내기·가져오기에 담지 않고 기본값 복원 때 남긴다(LOCAL_PROJECT_KEYS). resolve가 settings.linkedRepos로 합쳐 주고 없으면 []이다. 설정 패널 "프로젝트"(SettingsPanel의 LinkedRepos)가 `연결 N / 3개`와 추가·해제를 보여주고, 메인의 autopilot:add-linked-repo(폴더 선택 → getLinkedRepoError로 Git 루트·같은 프로젝트·폴더 이름 중복 거부)·remove-linked-repo가 저장하며 실행 중에는 거부한다. 시작 화면과 진행 화면에는 연결 저장소가 있을 때만 한 줄(shell/LinkedRepoPeek, `연결 저장소 N개 · 이름들`, 누르면 설정을 연다)이 뜨고, 엔진은 시작할 때 `[설정] 연결 저장소 N개: 이름들` 로그를 남긴다. 시작할 때 launchRun이 각 경로가 아직 Git 루트인지 확인하고 getCliArgs가 `--link-project`로 넘긴다. accountId는 전역 값이 새 탭의 기본 계정이고, 프로젝트 파일에는 그 탭이 고른 계정이 따로 들어간다(SCHEDULES_KEY처럼 OVERRIDABLE_KEYS 밖의 ACCOUNT_KEY라 설정 범위 줄·덮어쓴 키 목록에는 나오지 않는다). 화면과 시작·예약은 선택한 프로젝트 기준으로 합친 값(store.resolve().settings)을 쓰고, 화면에는 덮어쓴 키(overridden)와 전역 값(globals)도 함께 보낸다(autopilotIpc.getSettingsView). 프로젝트는 고를 때 저장하고, 시작할 때·실행 중 set에 성공할 때·예약을 저장할 때 고른 값은 전역 값과 다른 것만 프로젝트에 기억하며(store.remember) 전역 값과 같아지면 덮어쓴 값을 지운다. 프로젝트를 고르지 않았으면 전역에 기억한다.
- 설정 파일은 settingsStore.cjs(스키마·기본값·검증·마이그레이션)와 jsonFile.cjs(저장)가 맡는다. 쓰기는 임시 파일에 다 쓰고 디스크에 반영한 뒤 교체하며, 읽을 수 있던 직전 파일만 .bak으로 남긴다(깨진 파일이 좋은 백업을 덮지 않는다). 앱을 켤 때 전역 파일의 손상을 발견하면(프로젝트 파일은 읽을 때) 깨진 파일을 .corrupt로 옮기고 .bak으로 복구하며(없으면 기본값) 화면이 안내를 한 번 보여준다. 저장 형식은 `version` 키로 구분하고(없으면 0, 전역은 지금 3) 형식을 바꾸는 변경은 settingsStore의 MIGRATIONS에 더하며 앱을 켤 때 upgrade()가 한 번 올려 저장한다(0→1은 변환 없음, 1→2는 전역의 작업 하나를 마지막으로 고른 프로젝트의 작업으로 옮김, 2→3은 마지막으로 고른 프로젝트를 열린 탭 하나로 둠). 저장은 `update(patch)`로 읽은 직후의 값에 바뀐 키만 얹어 await 사이에 다른 곳이 저장한 값을 되돌리지 않게 한다. 설정 내보내기·가져오기·기본값 복원은 store의 exportData·importData·resetPreferences가 맡는다. 내보낸 파일은 `{app: "AutoPilot", kind: "settings", version, global, projects}`이고 이 PC에서만 뜻이 있는 키(MACHINE_KEYS: projectDir·tabs·accounts·accountId·claudeDir·launchAtLogin·createParentDir·railWidth. 프로젝트가 고른 계정도 내보내지 않고, 가져오기·기본값 복원은 이 PC에 있던 값을 남긴다)와 PC를 끄는 postRunAction(NON_PORTABLE_KEYS)은 담지도 가져오지도 않는다(새 전역 키는 기본으로 오가므로, 이 PC에만 뜻이 있거나 위험한 키는 MACHINE_KEYS에 더한다). 가져오기는 파일에 있고 검증을 통과한 키만 바꾸고 프로젝트는 getProjectError를 통과한 폴더만 적용하며(최대 200개, 파일 2MB 이하), 덮어쓰는 가져오기·되돌리기는 화면의 확인 모달을 먼저 거치고 실행 중에는 메인도 거부한다(autopilot:export-settings·import-settings·restore-defaults). 가져온 뒤 로그인 자동 실행이 켜져 있으면 트레이 상주를 다시 켠다. tests/checkDesktopSettings.js가 검증한다.
- 사용량 한도 연장 상한(extendLimitMinutes, 분, 0은 제한 없음, 덮어쓸 수 있는 키)은 연장(extendOnLimit)이 켜졌고 0보다 클 때만 엔진에 `--max-extend-minutes`로 넘긴다(engineArgs.cjs의 getCliArgs. 엔진 인자 조립은 이 순수 모듈이 맡고 tests/checkDesktopRunner.js가 검증한다). 허용 값은 settingsStore의 EXTEND_LIMIT_CHOICES다.
- 커밋 접두어(commitPrefix)와 작업 브랜치(workBranch)는 덮어쓸 수 있는 키이고 값이 기본값과 다를 때만 엔진에 `--commit-prefix`·`--branch`로 넘긴다(engineArgs.cjs). 검증은 engineArgs의 isValidCommitPrefix·isValidWorkBranch가 맡고 엔진 util.js와 같은 규칙이어야 하며(tests/checkDesktopRunner.js가 값을 대조) 입력 줄(ui/features/settings/GitGroup.jsx)은 Enter와 포커스를 떠날 때 저장하고 이유는 메인이 돌려준 문구(autopilotIpc의 SETTING_ERROR_MESSAGES)를 줄 아래에 보인다.
- 종료 신호는 같은 엔진의 stop, 실행 중 회차 실행 값 변경은 set(다음 회차부터 적용), 강제 종료는 Windows taskkill /T /F(그 외 SIGTERM)다. set은 늘 `--runner --model --effort --codex-model --codex-effort`를 함께 보내고, Codex의 빈 값은 `default`로 보낸다(러너의 setRoundOptions).
- 실행 에이전트(runner, 덮어쓸 수 있는 키, claude·codex, 기본 claude)는 유지 보수에서 작업할 AI이고, 신규 개발은 단계마다 mains가 정하므로 runner를 보내지 않는다. 모델과 노력(추론)은 입력창의 AI 알약 둘(features/composer/AiPills, #ai-pill-claude·#ai-pill-codex)이 맡고 둘 다 늘 보인다(단계 선택과 무관하다). 알약은 제공자 로고(Symbols의 logo-claude·logo-openai, 채운 모양이고 Claude 로고는 브랜드 색)·모델·노력(추론) 이름과 파형을 묶고, 끝에 역할 표시를 붙인다(유지 보수에서 작업하는 쪽은 `메인`, 실행 중에는 일하는 쪽에 도는 고리와 `작업 중`(신규 개발은 `<단계> · 메인`), 협의·브레인스토밍을 받는 쪽에 `보조`). 팝오버(#ai-popover-<제공자>)는 위에서부터 머리(로고·이름)·모델 목록·노력(추론) 슬라이드·맨 아래 줄이고, 자리가 모자라면 모델 목록만 줄어든다(목록 안쪽 스크롤). 맨 아래 줄은 유지 보수에서는 `이 AI로 작업하기` 스위치(composer.setRunner, 하나를 켜면 다른 쪽이 꺼지고 실행 중이면 다음 회차부터 적용. Codex를 쓸 수 없으면 잠기고 이유가 보인다)이고 신규 개발에서는 이 AI가 메인인 단계를 보여 주기만 한다(바꾸는 곳은 단계 문장). Claude는 계열 줄 아래에 공식 목록(hooks/useModels, 설정의 모델 버전과 같은 /v1/models)의 버전 줄이 이어지는 목록이다(버전을 고르면 그 계열을 그 버전으로 고정한다. 고정은 설정의 modelVersions에 저장되고 실행 중에는 바꿀 수 없어서, 실행 중에는 고정한 계열의 줄과 버전 줄이 잠기고 이미 고정한 그 버전을 다시 고르는 것만 된다. 계열 줄은 최신 버전을 따라가며 고르면 고정이 풀린다). Codex는 한 줄 목록(기본 모델 + autopilot:get-providers의 models, 쓸 수 없으면 이유)이다. 모델은 AI마다 따로(model·modelId·codexModel) 정하고, 고른다고 runner가 바뀌지는 않는다. get-providers의 codex는 models([{id, label, defaultEffort}], models_cache.json)와 defaults({model, effort}, config.toml 맨 위 값)를 함께 주어, 기본 모델 줄·알약과 추론의 기본이 지금 쓰일 값을 보인다(buildSteps.getCodexDefaults). 노력(추론)은 다섯 단계(Low·Medium·High·Extra High·Max)이고 단계마다 이름·설명·태그가 lib/effortLevels.js의 LEVEL_INFO에, 슬라이드는 components/EffortSlider에 있다(Claude는 EFFORT_LEVELS 인덱스, Codex는 CODEX_EFFORT_LEVELS 값). Codex는 `Codex 설정 따르기` 스위치(빈 값, 파형 점선)를 켜면 슬라이드가 잠기고 설정이나 모델의 기본 단계를 보인다. 팝오버와 슬라이드는 그 AI가 부르는 이름(노력 · 추론, viewFormat의 EFFORT_TERMS)을 쓰고 단계 이름은 formatEffort(단계, 제공자)가 정한다(둘 다 xhigh는 Extra High). Extra High는 주황, Max는 붉은 선과 한 번 도는 고리로만 알린다(미터·불꽃 같은 장식은 두지 않는다).
- 실행 중에는 실행 에이전트·model·effort를 고르는 즉시 set으로 보낸다(Effort는 팝오버의 단계를 누를 때 한 번). 전달 중에 또 바뀌면 마지막 선택만 한 번 더 보낸다(composerStore의 applyRoundOptions). 러너 상태의 runner·model·effort는 지금 회차를 돌리는 쪽의 값이고(Codex 회차 시작 줄의 `기본값`은 빈 값), requested는 `{runner, model, effort, codexModel, codexEffort}`다. 적용 대기 문구는 requested에서 고른 쪽의 값과 지금 회차 값을 비교한다(ApplyNote).
- 대시보드는 회차 시작 로그의 (model X, effort Y)를 적용 중인 값으로, 마지막으로 set에 성공한 값을 요청 값으로 본다. 둘이 다르면 적용 대기로 표시한다.
- 모델은 화면에서 계열 별칭(MODEL_CHOICES, 최신 버전)만 고르고, 설정 패널의 "모델 버전"(#model-versions, ui/features/settings/ModelVersions.jsx)이 계열마다 모델 ID를 고정한다(modelVersions는 덮어쓸 수 있는 키라 고른 설정 범위에 묶음 통째로 저장하고, 비면 별칭). 별칭→ID 변환은 메인(autopilotIpc.resolveModel)이 시작·set에서만 하고 settings.model에는 계열을 저장한다. 엔진·러너 state의 model은 ID일 수 있어 화면(composerStore·viewFormat)이 getModelFamily·formatModelName으로 계열과 이름을 읽는다. 고정은 실행 중에 막고 메인도 거부한다(autopilot:update-settings).
- 버전 목록은 claudeAccount.createAccountReader().getModels()가 계정 토큰으로 공식 `GET /v1/models`(anthropic-version 헤더 필요)를 읽어 1시간 보관한다. ID 형식(MODEL_ID_PATTERN)을 벗어난 항목은 걸러내고 실패하면 이전 목록을 유지한다. 새 모델은 목록이 따라오지만 새 계열(line)은 별칭 라디오·MODEL_CHOICES·viewFormat의 MODEL_LABELS·마크를 함께 더해야 보인다. tests/checkDesktopRunner.js가 가짜 fetch로 검증한다.
- 허용 값은 autopilotRunner.cjs의 MODEL_CHOICES·MODEL_ID_PATTERN·EFFORT_CHOICES·BUILD_PHASES·PHASE_LABELS, settingsStore.cjs의 POLICY_CHOICES, engineArgs.cjs의 MODES·GATE_PHASES·SKIPPABLE_PHASES·ALLOW_KEYS·DESIGN_FORMATS·ON_FAIL_PATTERN·MAX_RUN_DAYS와 DEFAULT_*, 화면의 ui/lib/constants.js(MODEL_FAMILIES·EFFORT_LEVELS·POLICIES·MODES·BUILD_PHASES·PHASE_LABELS·GATE_PHASES·SKIPPABLE_PHASES·ALLOW_KEYS·DESIGN_FORMATS·ON_FAIL_CHOICES와 DEFAULT_*)이며 엔진 config.js와 함께 바꾼다. tests/checkDesktopRunner.js가 값과 기본값을 대조한다.

## 계정

### 프로필과 사용량 조회

- 조회는 메인 프로세스의 claudeAccount.cjs가 계정마다 하나씩(accountIpc.cjs가 관리) 한다. 그 계정 설정 폴더의 .credentials.json(macOS는 키체인도) 토큰으로 비공식 엔드포인트 api.anthropic.com/api/oauth/usage·/api/oauth/profile 두 곳만 부른다.
- 앱을 켤 때(startAccountWatch, 스모크 테스트 제외) 모든 계정을 한 번 읽어 메인에 보관하고 5분마다 다시 읽어 autopilot:account({id, account})로 화면에 보낸다. 새로 고침(autopilot:refresh-account)은 15초 안의 재요청을 막는다. 일부만 실패하면 성공한 쪽만 갱신하고 이전 값은 유지한다.
- 토큰은 이 모듈 밖으로 내보내거나 로그에 쓰지 않고 읽기만 한다. 앱이 refresh하지 않는다(refresh token은 회전해서 같은 토큰으로 두 번 갱신하면 저장된 로그인이 폐기되고, CLI는 프로세스끼리 갱신 잠금을 나눠 쓰지만 앱은 그 잠금에 끼지 못한다). 갱신은 CLI에 맡긴다.
- Anthropic 정책(Claude Code 문서의 Legal and compliance)은 개발자가 Claude.ai 자격 증명·세션 토큰을 수집·보관·중개하는 것을 막고 로그인은 Anthropic의 흐름으로 끝내라고 한다. 그래서 refresh token은 물론 `claude setup-token`의 장기 토큰도 앱이 저장하지 않는다. 장기 토큰은 사용자가 OS 환경 변수 CLAUDE_CODE_OAUTH_TOKEN으로 직접 쓰는 방법만 안내하고, 이 토큰은 사용량·프로필 조회에 필요한 user:profile 권한이 없어 그 조회(/api/oauth/usage·profile)가 403이다(/v1/models는 된다).
- 액세스 토큰은 수명이 약 8시간이라 만료되면 claudeCli.renewCredentials가 가장 작은 `claude -p` 요청 한 번(haiku, effort low, 도구·사용자 설정·MCP를 빼서 입력 약 3k 토큰, 약 $0.0006)으로 CLI가 직접 갱신하게 맡기고 다시 읽는다. 실행·로그인 중에는 하지 않고 계정마다 30분에 한 번만 시도하며, 갱신이 안 되면 그때 안내를 낸다.
- 로그인 만료 안내: 저장된 로그인에는 만료일이 있고(.credentials.json의 refreshTokenExpiresAt, ms 시각) 만료되면 `/login`만이 복구다. claudeAccount가 그 시각 값만 읽어 계정 스냅샷의 loginExpiresAt(모르면 0)으로 보내고, 사용량 조회가 실패해도 파일에서 읽는다. 화면은 viewFormat.describeLoginExpiry가 만든 문구를 프로필 패널의 #login-expiry 줄로 보여주고, 만료 3일 전(LOGIN_EXPIRY_WARN_MS, Claude Code의 경고와 같다)부터는 컴포저 위 #login-expiry-banner와 프로필 패널의 다시 로그인 버튼을 띄운다. 안내 줄의 버튼(accounts.reloginBeforeExpiry)은 로그인 뒤 시작을 잇지 않고, 로그인은 알고 있는 이메일을 `claude auth login --email`로 미리 채운다(claudeCli의 LOGIN_EMAIL_PATTERN을 통과한 값만. CMD 래퍼 명령줄에 들어가므로 검사한다. 인증은 대신하지 않아 코드는 사용자가 입력한다).
- 만료 화면 시험: `npm run dev -- --debug-login-expiry=<값>`(30m·5h·2d, 이미 만료는 -1m)이 앱을 켠 시각 기준의 만료 시각을 모든 계정에 돌려준다(claudeAccount.parseLoginExpiryFlag, 형식이 틀리면 무시). 패키지 앱(app.isPackaged)에서는 읽지 않고, tests/tools/ui의 login-expiry 장면이 같은 화면을 가짜 데이터로 찍는다.
- 프로필에는 아바타 URL이 없다. 사용량은 limits[](session·weekly_all·weekly_scoped)를 기준으로 읽고 없으면 five_hour·seven_day로 대신한다. 형식이 바뀌어도 앱이 깨지지 않게 실패 안내만 낸다.
- 엔진·로그 형식과는 무관하다. tests/checkDesktopRunner.js가 가짜 fetch로 검증한다.

### 멀티 계정

- 기본 계정은 "Claude 데이터 폴더"(기본 .claude)에 로그인된 계정이다. 이 폴더는 설정 패널에서 고른 경로(settings.json의 claudeDir), 없으면 환경 변수 CLAUDE_CONFIG_DIR, 없으면 ~/.claude 순으로 정하고(accountStore.resolveBaseDir) 환경마다 달라도 폴더 선택·자동 감지로 맞춘다.
- 엔진의 --config-dir 기본값이 ~/.claude이므로 기본 계정이 다른 위치면 그 폴더를 --config-dir로 명시한다. 직접 고른 폴더가 없어졌으면 시작하지 않는다. 시작할 때 선택한 계정이 기본 계정이 아니면 엔진에 --config-dir <그 폴더>를 넘긴다.
- 추가한 계정은 앱 데이터 폴더의 accounts/<acct-8자리16진수>/ 설정 폴더 하나씩이다(로그인 정보·.claude.json은 계정마다 따로). settings.json에는 {id, label, shared} 목록(accounts)과 새 탭의 기본 계정(accountId), 프로젝트 파일에는 그 탭이 고른 계정(accountId)만 저장하고 계정 폴더 경로나 토큰은 저장하지 않는다. 폴더는 id로만 정해서(id 형식을 검사한다) 설정 파일로 임의 경로를 가리킬 수 없게 한다.
- 계정 추가 때 "기본 .claude의 메모리·지침·스킬 함께 쓰기"(기본 켬)를 고르면 기본 폴더의 projects(메모리·세션 기록)·skills·plugins·commands·agents는 junction(관리자 권한 불필요)으로, CLAUDE.md·settings.json은 심볼릭 링크(안 되면 복사)로 연결한다(accountStore.linkSharedData). 이미 있는 실제 폴더·파일은 건드리지 않는다. 앱을 켤 때·폴더를 바꿀 때 다시 이어 주며 새 위치에 없는 항목의 낡은 링크는 끊는다.
- 계정 제거는 연결을 먼저 끊고 폴더를 지워 기본 .claude의 데이터를 지우지 않는다(테스트로 보장).
- 로그인은 claudeCli.cjs가 CLAUDE_CONFIG_DIR을 그 폴더로 지정해 `claude auth login --claudeai`를 실행한다(브라우저는 CLI가 연다). 출력에서 찾은 로그인 주소(claude.com·claude.ai·anthropic.com의 https만)를 "브라우저에서 열기"로 열 수 있게 알리고, 브라우저가 코드를 보여 주면 입력칸의 코드를 CLI의 stdin으로 전달한다. 로그인 코드는 로그에 남기지 않는다. 끝나면 `claude auth status --json`으로 로그인 상태를 확인하고, 새 계정이 실패·취소되면 만든 폴더를 지운다(못 지워도 목록에서 빼고 결과를 알려 화면이 로그인 대기에 멈추지 않게 한다).
- 시작 전에는 기본 계정을 포함해 선택한 계정의 로그인을 `claude auth status --json`으로 확인한다(accountIpc.getRunAccount, 종료 코드는 보지 않는다). 안 돼 있으면 시작하지 않고 LOGIN_REQUIRED를 돌려준다. 렌더러는 이때 안내 줄(#login-banner)에 로그인 버튼을 보이고, 누르면 그 계정의 로그인을 시작해 주소·코드 입력이 있는 프로필 패널을 열며, 로그인이 성공하면 멈췄던 시작을 이어간다.
- 실행·로그인 중에는 계정 선택(그 탭이 실행 중일 때)·추가·제거·로그인·데이터 폴더 변경(어느 탭이든 실행 중일 때)을 막는다(메인도 거부한다). 한도 회피를 위한 자동 계정 전환은 하지 않는다.
- tests/checkDesktopAccounts.js가 가짜 claude로 검증한다.

### 플랫폼 범위

- 배포는 Windows exe(포터블·설치형), macOS dmg·zip, Linux AppImage·deb이고 계정 코드는 비-Windows에서도 돌도록 짠다. claudeCli.findClaude는 비-Windows에서 실행 권한을 확인하고, junction은 Windows 밖에서 디렉터리 심볼릭 링크로, 프로세스 종료는 Windows taskkill·그 외 SIGTERM으로 하며, CMD 래퍼 처리는 Windows만 한다.
- 작업표시줄 도는 표시는 Windows만이다(systemIntegration의 syncTaskbarOverlay). 집계 진행 모드가 normal·indeterminate일 때만 setOverlayIcon으로 12프레임(drawOverlayBitmap이 코드로 그린 32x32 BGRA, TRAY_ICON_SCALE 2배)을 120ms마다 바꾸고, 그 밖에는 지운다. systemPreferences.getAnimationSettings().prefersReducedMotion이면 타이머 없이 한 장만 보인다. tests/checkDesktopSystem.js가 비트맵을 검증하고, 눈으로 볼 때는 프레임을 PNG로 펼쳐 확인한다.
- 로그인 여부는 저장 위치가 플랫폼마다 달라 파일이 아니라 `claude auth status --json`으로 확인한다.
- 창 아이콘은 Windows가 .ico, 그 밖은 .png다. 트레이 아이콘은 2배 크기(TRAY_ICON_SCALE)로 만들어 고해상도에서 흐려지지 않게 한다. 서체 목록(--sans·--mono)에는 macOS·Linux 시스템 서체를 대체로 둔다. Cmd+Q·시스템 종료(before-quit)는 트레이 숨기기가 아니라 종료 확인을 거친다. Linux는 트레이를 지원하지 않는 데스크톱이면 트레이로 숨긴 창을 다시 열 수 없으므로(두 번째 실행으로 열 수는 있다) README에 알린다.
- Windows·Linux는 로그인 정보가 설정 폴더의 .credentials.json이고, macOS는 키체인(서비스 `Claude Code-credentials-<설정 폴더 경로 SHA-256 앞 8자>`, 기본 폴더는 접미사 없는 옛 이름도)이다. claudeAccount는 두 곳을 모두 읽어 만료가 더 늦은 로그인을 쓴다(keychainCredentials.cjs가 `/usr/bin/security find-generic-password -s <서비스> -w`로 읽기만 한다. 다른 계정의 폴더는 옛 이름을 읽지 않는다). 키체인을 읽지 못하면(접근 거부·시간 초과, 항목이 없는 종료 코드 44는 제외) KEYCHAIN_BLOCKED 안내를 내고 접근 허용 창이 5분마다 뜨지 않도록 한 시간 동안 다시 묻지 않는다. 서비스 이름 규칙은 Claude Code의 비공식 동작이라 바뀔 수 있다.
- Finder·Dock·데스크톱 아이콘으로 연 macOS·Linux 앱은 터미널의 PATH를 받지 못한다. main.cjs가 앱을 켤 때(스모크 테스트 제외) loginShellPath.applyLoginShellPath로 로그인 셸(`$SHELL -ilc`, 5초 제한)의 PATH와 흔한 설치 위치(~/.local/bin·~/.claude/local·npm 전역·Homebrew 등)를 현재 PATH 뒤에 합쳐 process.env.PATH에 쓰고, 엔진과 claude를 띄우는 자식 프로세스가 이어받는다(findClaude·엔진의 getExecutablePath는 PATH만 본다). Windows는 건드리지 않는다.
- Linux는 WSL로 tests/checkDesktopAccounts.js·checkDesktopRunner.js·checkDesktopView.js를 확인했다. macOS는 키체인 읽기를 가짜 security로 검증하고, CI의 macOS 러너(CI 환경 변수가 있을 때)는 임시 키체인으로 진짜 security의 출력·종료 코드를 확인한다. 실제 macOS 앱에서 사용량 조회까지는 사람이 직접 확인한 적이 없다.

## 새 프로젝트 만들기

- 레일의 "새 프로젝트"(#new-project-toggle, "프로젝트 열기" 위)가 본문을 새 프로젝트 화면(features/create/NewProjectView, uiStore의 newProject, body[data-creating])으로 바꾼다. 모달이 아니고 컴포저는 숨긴다. 보는 동안 레일의 탭은 고른 것이 없게 그리고(첫 탭이 Tab 키 자리), 탭을 누르거나 프로젝트를 열면 닫힌다. 입력은 stores/newProjectStore가 만들거나 처음부터 다시 쓸 때까지 들고 있어 다른 탭을 봤다 와도 남는다.
- 흐름은 "쓰기보다 고르기"다(빈 칸 8개짜리 첫 시안은 쓰기 힘들다는 피드백으로 바꿨다). 1단계는 한두 줄(예시 칩으로 채울 수 있음)과 어디서 쓰나요 칩(projectDraft.PLATFORMS, 아직 몰라요는 다른 것과 함께 고르지 않음)과 만들 위치. "초안 만들기"는 Claude가 나머지를 채우고, "직접 다 쓸게요"는 빈 다듬기로 간다. 2단계(초안 다듬기)는 칩(넣은 것은 흰 칩·체크, 추천은 회색·+, aria-pressed)을 눌러 넣고 빼고 짧게 더한다(Enter, 여러 줄 붙여 넣기는 줄마다). 기술 스택은 추천대로·나중에(기획에서 정함)·직접이다. 오른쪽은 만들 brief.md를 DocPreview로 그대로 보인다. 초안을 쓰는 동안(isDrafting)에는 다음 단계(다듬기)의 틀이 바로 나와 칸마다 반짝이는 자리 표시가 깔리고(.np-fill, 오른쪽 brief.md 자리는 DocSkeleton) 머리글(DraftProgress)의 막대가 흐르며 `그만두기`가 있다. 응답이 언제 올지 알 수 없어 쓰는 동안에는 칸 수 진행을 말하지 않는다. 응답이 오면(isRevealing, REVEAL_MS 3.6초) 칸이 위에서부터 0.45초 간격으로 채워진다: 자리 표시가 걷히고 쓰는 칸만 파란 테두리로 빛나며 글은 왼쪽부터 드러나고 칩은 하나씩 떠오르고 brief.md가 위에서 아래로 드러나며, 머리글은 `n / 4칸`을 센다. 움직임 줄이기에서는 응답이 오면 바로 걷힌다. 초안이 실패하면(로그인 없음·시간 초과·읽을 수 없는 답) 적은 한두 줄을 한 줄 요약으로 두고 이유를 다듬기 위에 알린다. 그만두기 뒤에 늦게 온 답은 버린다.
- 초안(autopilot:draft-project)은 메인이 새 탭의 기본 계정(전역 accountId, accountIpc.getDraftAccount가 로그인 확인)으로 claudeCli.askClaude를 한 번 부른다. sonnet·effort low·도구·사용자 설정·MCP 없이(renewCredentials와 같은 최소 호출) --output-format json이고, 질문은 사용자 글이 섞여 있어 명령줄이 아니라 stdin으로 넘긴다(CMD 래퍼에 들어가지 않게). 90초 제한, 한 번에 하나(새 요청·autopilot:cancel-draft가 앞의 것을 끝낸다). 답은 projectDraft.parseDraft가 JSON을 찾아 칸마다 다듬는다(글자·개수 상한, 제어 문자, 모르는 실행 환경, 폴더 이름은 영문 소문자·숫자·하이픈). 다른 AI 제공자를 붙일 때는 이 질문·해석을 그대로 쓰고 부르는 쪽만 더한다.
- 추천 예시(autopilot:suggest-examples): 1단계의 예시 칩은 기본 예시(actions/newProject의 EXAMPLES 8개)를 그대로 두고, `Claude 추천` 줄의 `추천 예시 받기`·`다시 받기`만 메인이 claudeCli.askClaude를 haiku·45초 제한으로 한 번 부른다(초안과 같은 최소 호출·기본 계정, 한 번에 하나). 질문(projectDraft.getExamplesPrompt)은 이미 보인 이름(exclude)과 겹치지 않게 부탁하고 답은 parseExamples가 JSON 배열에서 이름 14자·설명 120자·실행 환경 2개로 다듬어 5개까지만 받는다(읽을 수 없으면 EXAMPLES_INVALID). 실패해도 쓰던 예시는 남고 이유는 칩 줄 아래에 보인다. 추천은 newProjectStore.suggestions이고 처음부터 다시 쓰기에도 남는다.
- 화면 구성: 만들 위치는 폴더 아이콘·전체 경로·`폴더 바꾸기`가 한 덩어리인 단추(FolderField, 1단계는 실행 환경 아래·2단계는 이름 아래 전체 폭)다. 2단계 왼쪽은 `기본 정보`·`쓰는 사람과 기능` 묶음만 펴 두고 하지 않을 것·기술 스택·참고할 것은 `더 정하기`(newProjectStore.isMoreOpen)에 접어 요약(하지 않을 것 N개 · 기술 스택 선택)을 보인다. 오른쪽 brief.md 미리보기 위에는 `기획 설명서`가 무엇인지(기획이 가장 먼저 읽는 한 장짜리 문서, 만들면 첫 커밋이 됨) 알리는 머리글이 있고 미리보기는 칸 안에서 스크롤한다. 단계가 바뀌면 새 단계가 아래에서 떠오르며(np-step-in), 순서 표시의 선이 차오르고 만드는 중에는 세 번째 칸이 켜진다.
- 만들기(autopilot:create-project)는 렌더러가 이름·brief·작성자만 보내고 위치는 보내지 않는다. 위치는 이번 실행에서 대화상자(autopilot:pick-create-dir)로 고른 폴더, 없으면 마지막으로 만든 위치(전역 createParentDir, 이 PC에서만 뜻이 있어 MACHINE_KEYS), 없으면 문서 폴더다(autopilot:get-create-info가 위치와 git의 전역 작성자를 알려준다). 탭이 MAX_TABS면 디스크를 건드리기 전에 거부한다. projectFiles.createProject가 이름(projectDraft.getProjectNameError: Windows 금지 문자·예약 이름·끝 점/빈칸·64자)과 작성자를 검사하고, 폴더가 있고 비어 있지 않으면 거부하며(빈 폴더는 씀), git init + HEAD를 main으로(옛 git도 되게 init -b 대신 symbolic-ref) → 작성자를 받았으면 이 저장소에만 user.name·user.email → docs/autopilot/brief.md(sanitizeBrief: 제어 문자 제거·32KB) → commit "init: 프로젝트 초안(brief.md)". 도중에 실패하면 새로 만든 폴더는 통째로, 이미 있던 빈 폴더는 만든 .git·docs만 지운다. 성공하면 새 탭으로 열고 그 프로젝트에 mode=build와 tasks=brief.md 내용을 기억해(remember. 실행 환경을 서버 · API, CLI · 도구만 골랐으면 skip=[design]도 기억한다. projectDraft.getRecommendedSkip이 정하고 렌더러는 platforms만 보낸다) open-tab과 같은 결과를 돌려준다. 화면은 신규 개발 시작 전 화면으로 가고 기획 시작은 사용자가 누른다. 기획 단계는 brief.md를 먼저 읽는다.
- 검증: tests/checkDesktopRunner.js(checkProjectDraftRules·checkCreateProject, 임시 폴더의 진짜 git), checkDesktopAccounts.js(checkAskClaude, 가짜 claude), checkDesktopStores.js(checkNewProject), checkDesktopUi.js(checkTagChips), tests/tools/ui의 new-project-* 장면.

## 지난 실행(기록 보기)

- 시작 화면(#recent)에 최근 3개, 설정 패널의 지난 실행 보기·#archive-all의 전체 보기가 시트(#archive)로 목록과 상세(채팅 모양 #archive-chat)를 연다.
- 원본은 대상 프로젝트의 .autopilot/progress/<날짜>/autopilot_*.log뿐이다. 별도 저장소를 두지 않는다(보관 기간은 엔진의 logRetentionDays를 따르고, 앱의 설정 logRetentionDays(7·14·30·90·180일, 기본 30, 덮어쓸 수 있는 키)를 기본값과 다를 때 `--log-retention-days`로 넘긴다).
- 읽기는 메인 프로세스의 runHistory.cjs(listRuns·readRun)가 하고 IPC는 autopilot:list-runs·read-run·open-run-file이다. 렌더러가 보내는 값은 실행 id(`YYYY-MM-DD/autopilot_*.log`)뿐이고 getRunFiles가 형식을 검사해 진행 기록 폴더 안의 경로로만 바꾼다. 열기(리포트·원본 로그)는 projectFiles의 isProjectReportFile·isProjectLogFile로 실제 경로까지 검사한다. 목록의 심볼릭 링크·junction은 따라가지 않는다.
- 시작 시각은 폴더 날짜와 파일 이름의 HHmmss, 끝 시각은 파일 수정 시각이다(7일을 넘기면 알 수 없음). 요약 문장은 viewFormat.describePastRun이 만든다. 대화 변환(viewFormat.buildTranscript)은 알아볼 수 없는 줄을 건너뛰고 1500개까지만 둔다.
- 깨진 로그 대응: 잘못된 UTF-8·BOM·CRLF·제어 문자·2000자 넘는 줄을 정리한다. 16MB를 넘으면 끝부분만 읽고(isPartial) 상세는 최근 20000줄까지 보낸다. 비었거나 알아볼 줄이 없으면 isEmpty, 읽기 오류는 isUnreadable, 끝맺음 줄이 없으면 reason이 비어 `끝맺음 없음`이다. 실행 중인 엔진의 로그(isActive)는 끝맺음이 없어도 비정상으로 보지 않는다.
- 설정 패널의 "로그 보관"(StorageGroup)은 보관 기간과 지금 차지하는 용량(runHistory.getRunUsage, autopilot:get-run-usage. 보관 기간이 지나 정리될 몫 포함)을 보여주고 "지금 지우기"(runHistory.pruneRuns, autopilot:prune-runs)로 그 몫을 바로 지운다. 정리 기준은 엔진 pruneRunFiles와 같다(오늘 0시에서 보관 기간만큼 거슬러 올라간 날짜보다 이른 폴더의 autopilot_*.log·report_*.html만, 링크는 따라가지 않음. 진행 중인 로그·완료 마커·보관한 진행 기록 원본·다른 파일은 건드리지 않고 비게 된 날짜 폴더만 지움). 되돌릴 수 없어 화면의 확인 모달을 먼저 거친다.
- 삭제(autopilot:delete-run, runHistory.deleteRun)는 화면의 확인 모달(actions/runs.js의 deleteArchiveRun)을 거쳐 그 실행의 로그·리포트만 지운다. 진행 중인 실행(isActive)은 거부하고 날짜 폴더는 비었을 때만 지운다(완료 마커·보관 원본은 건드리지 않는다).

## 연속 실행

- 시작 화면 인사(ReadyView의 Greeting)의 안내 문구 앞에 연속 실행 문장 한두 개를 붙인다(viewFormat.describeStreak). 숫자 위젯·달력·막대는 두지 않고 문장만 쓴다(시안 words-only). 말하지 않아도 되는 때는 아무것도 붙이지 않는다.
- 하루로 세는 기준은 그날(날짜 폴더 이름, 밤샘 실행은 시작한 날) 첫 회차를 시작한 실행 로그가 있는 것이다(runHistory.listRunDays). 시작 단계에서 실패해 회차가 없는 실행과 읽을 수 없는 로그는 세지 않고 커밋이 없는 실행은 센다. 프로젝트마다 센다.
- 날짜 목록은 userData/streaks.json(`{version, projects: {<프로젝트 키>: {days}}}`, 최대 1000일)에 보관해 로그가 보관 기간이 지나 지워져도 긴 기록이 남는다(streakStore.refresh. 이미 적은 날은 다시 읽지 않아 지난 로그는 처음 한 번만 훑고, 겹친 요청은 하나씩 처리하며, 깨진 파일은 비운 것으로 보고 남은 로그에서 다시 만든다). IPC autopilot:get-streak-days(projectDir)는 `{ days }`(오름차순)만 돌려주고, 연속 일수는 화면이 오늘 날짜(useClock)로 센다(viewFormat.getStreakSummary. 자정이 지나면 다시 읽지 않아도 문구가 바뀐다). loadRecentRuns가 loadStreakDays를 함께 부른다(시작·탭 전환·실행 종료 뒤).
- 문장 규칙: 어제나 오늘까지 이어진 연속이 2일 이상이면 "어젯밤까지 N일째 돌았어요."(오늘 돌았으면 "오늘까지")이고, 이전 최장 기록(2일 이상)을 넘었으면 그 기록을 함께 알린다. 하루만 이어졌으면 어제 돌았다는 말만 하고, 어제 쉬어서 끊긴 날(끊긴 연속이 2일 이상)에만 한 번 알리고 그 뒤로는 말하지 않는다. 쉬어도 이어 주는 날(휴식권)은 없다. 재촉하지 않는 말투를 지킨다.
- 검증: tests/checkDesktopStreak.js(날짜 수집·보관), tests/checkDesktopView.js(일수 계산·문장), tests/tools/ui의 stage-ready-streak* 장면.

## 성과 카드

- 마친 화면(FinishView)의 "카드 저장"(#done-card)이 마친 실행을 1200x630 PNG 한 장으로 저장한다(시안 sentence). Claude가 한 일을 말한 문장 하나를 크게(끝부분은 굵게, 마지막 줄 아래에 파란 밑줄), 아래에 사실 두 줄(언제 몇 시부터 몇 시까지와 프로젝트 이름, 커밋 수와 변경 줄 수)과 로고를 둔다. 장식을 더하지 않는 것이 이 카드의 핵심이다.
- 내용은 화면이 고른다(viewFormat.buildShareCard). 문장은 로그의 Claude 문장 중 이미 마쳤다고 말하는 것(과거형 해요체, 한글, 8~80자. 한 줄에 여럿이면 마지막 문장부터)을 마지막부터 찾고, 없으면 마지막 성과 줄("이전 → 이후", 이후 값을 굵게), 그것도 없으면 마친 화면의 안내 문장(describeFinish.lead)으로 대신한다. 커밋이 없으면 "이번에는 커밋을 남기지 않았어요", 시작 시각을 모르면(재연결 등) 시각 줄을 뺀다.
- 그리기와 저장은 메인이 한다(shareCard.cjs, IPC autopilot:save-card). 렌더러가 보낸 content는 sanitizeCardContent가 글자·길이·줄 수(문장 120자·사실 줄 80자 2개)만 받고(제어 문자는 공백), 저장 위치는 OS 저장 대화상자(기본 사진 폴더, getCardFileName)가 먼저 받는다(취소하면 그리지 않는다). 카드는 화면에 나타나지 않는 창(offscreen)에 desktop/shareCard.html·css·js를 로드해 그리고(window.renderCard가 글자를 채우고 글자 크기를 맞추며 마지막 줄을 재서 밑줄을 둔다. 줄바꿈은 text-wrap: balance) DevTools(Emulation.setDeviceMetricsOverride로 보이는 영역을 카드 크기로 고정하고 Page.captureScreenshot으로 그 영역)로 찍어 PNG로 쓴다. 창은 작업 영역보다 커지지 않아 capturePage는 폭이 좁은 화면(CI 러너의 1024px 등)에서 카드보다 작게 찍힌다. 카드 페이지는 자체 CSP(스크립트·스타일·이미지·서체 모두 self)이고 데이터는 executeJavaScript로만 넘기며 textContent로만 넣는다.
- 스모크 테스트가 숨긴 창으로 카드를 한 장 그려 1200x630인지 확인한다(checkCardRender). 이 창은 화면에 보이지 않는다. GPU가 없는 CI 러너에서는 숨긴 창의 캡처가 UnknownVizError로 실패하므로 스모크 테스트는 하드웨어 가속을 끄고 돌린다(main.cjs). 검증: tests/checkDesktopCard.js(sanitize·파일 이름), tests/checkDesktopView.js(문장 고르기·강조·시점·내용), tests/tools/ui의 stage-done-card 장면(IPC로 보낸 content와 저장 안내).
- 화면 배율 2(2400x1260)는 쓰지 않는다. 한 배율로 정했다.

## 새 버전 알림

- 설정의 새 버전 확인(checkUpdates, 기본 켬)을 끄면 확인하지 않고 알고 있던 안내를 거둔다(updateCheck의 isEnabled). 바꾸는 즉시 autopilot:set-preferences가 check()를 불러 켜면 바로 확인하고 끄면 칩을 숨긴다.
- 메인 프로세스의 updateCheck.cjs가 앱을 켤 때(스모크 테스트 제외)와 6시간마다 GitHub `releases/latest`(공개 저장소, 토큰 없음)의 태그를 app.getVersion()과 숫자로 비교한다. 더 높으면 {version, url}을 보관하고 바뀔 때만 autopilot:update로 화면에 보낸다. 조회 실패는 조용히 넘어가고 이전 값을 유지한다.
- 열 주소는 `^v?\d+\.\d+\.\d+$`를 통과한 태그로 직접 만든다(응답의 URL은 쓰지 않는다). 렌더러는 주소를 보내지 않고 autopilot:open-update만 요청한다.
- 실행 줄(#titlebar) 오른쪽 창 버튼 앞의 #update-chip(회색 칩, 파랑은 진행 중 표시 전용)이 누르면 그 릴리스 페이지를 연다. 자동 설치는 하지 않는다.
- tests/checkDesktopRunner.js가 가짜 fetch로 검증한다.

## 예약

- 레일의 예약 버튼(#schedule-toggle)이나 시작 화면의 한 줄(#schedule-peek)이 예약 시트(#schedule)를 연다. 시트는 지난 실행 시트와 같은 자리·같은 규칙이고(전체 기록·지난 실행·패널과 한 번에 하나만 열림, 스크림·Esc로 닫음) 목록과 폼을 번갈아 보여준다. 모달은 쓰지 않는다.
- 규칙은 scheduleRules.cjs(순수 함수, 시계·사용량을 인자로 받음), 주기 판단·상태 보관은 scheduler.cjs, IPC·실행 연결은 autopilotIpc.cjs다. 예약 목록은 전역 settings.json의 schedules와 프로젝트 파일의 schedules(합쳐 최대 8개, 읽을 때 normalizeSchedules가 올바르지 않은 항목을 버림)에, 판단 상태(마지막 시작·기억한 한도 리셋 시각·무장 여부)는 userData/schedule-state.json에 둔다.
- 시작 조건은 두 가지다. 정해진 시각(time)은 요일과 시각이 오면 시작하고 TIME_GRACE_MS(2시간) 안에서는 놓친 예약도 이어서 시작한다(앱이 늦게 켜졌거나 PC가 잠들었다 깬 경우). 한도 리셋(reset)은 5시간 또는 주간 한도가 리셋되면 한 번 시작하고 다음 리셋까지 기다린다. 리셋은 기억해 둔 resetsAt이 지났거나, 쓰인 한도가 다시 새 한도(응답에 항목이 없거나 resetsAt이 지났거나 사용률 1% 미만)로 읽힐 때 알아채고, 처음 본 한도가 이미 새 한도면 바로 무장한다. 리셋 시각이 지난 직후에는 사용량을 다시 읽어 남은 한도 조건을 판단한다.
- 공통 조건은 요일, 남은 한도(minRemaining, 5시간·주간 중 적게 남은 쪽이 N% 이상일 때만, 읽지 못하면 검사하지 않음), 실행 시간(duration)이다. minRemaining은 0~100의 정수(0은 검사 안 함), duration은 MIN_DURATION(30분, MIN_RUN_MS와 같다)~MAX_DURATION(23시간 59분, 종료 시각을 HH:mm로만 넘기므로 하루 안)의 정수 분이고 parseSchedule이 검증한다. 폼(ScheduleForm)의 알약은 자주 쓰는 값의 바로가기일 뿐이고 숫자 칸에 직접 입력한 값이 그대로 저장된다(입력 한계는 폼과 scheduleRules가 따로 갖는다). 리셋 예약에는 시작할 수 있는 시간대(from~to, 자정을 넘길 수 있고 요일은 시간대가 시작하는 날 기준)를 둘 수 있고, 종료 시각은 시간대가 닫히는 시각을 넘지 않게 맞추며 남은 시간이 MIN_RUN_MS(30분)보다 짧으면 시작하지 않는다.
- 예약마다 대상 프로젝트가 있다. 프로젝트 예약(scope가 project)은 저장할 때 달린 projectDir의 프로젝트(열린 탭)에서, 전역 예약은 그때 활성인 탭의 프로젝트에서 돈다(getScheduleDir). 바쁨·사용량·시작을 대상 프로젝트별로 판단하고(scheduler의 isBusy·getUsage·refreshUsage는 예약을 받고 getTargetKey로 프로젝트를 가른다) 한 판단 안에서 같은 프로젝트는 한 번만 시작한다. 대상 프로젝트가 열려 있지 않으면 시작하지 않고 이유를 알린다.
- 이미 실행 중이거나 시작을 진행 중이면 기다린다(isEngineBusy가 먼저 그 프로젝트의 살아 있는 엔진에 연결한다). 시작에 실패해도(로그인 필요 등) 같은 시작 시각을 다시 시도하지 않고 알림으로 이유를 알린다. 절전에서 깨어나면 5초 뒤 바로 판단하고, 평소에는 30초마다 판단한다.
- 예약은 덮어쓰기가 아니라 합집합이다. 전역 예약과 열린 모든 탭의 프로젝트 예약(scope가 project, projectDir이 붙는다)을 함께 보여주고(readAllSchedules), 저장할 때 scope와 projectDir로 전역 설정과 각 프로젝트 파일에 다시 나눠 쓴다(writeAllSchedules. 합쳐 최대 8개). 새 예약은 프로젝트를 골랐으면 그 프로젝트(활성 탭)의 예약이 기본이고, 수정으로 범위나 대상 프로젝트를 바꾸지는 않는다. 탭을 닫아 목록에서 빠진 예약의 판단 상태는 getKnownScheduleIds로 남겨 둔다.
- 예약 실행은 대상 프로젝트에 적용되는 작업·정책·모델·Effort·사용량 한도 연장 설정으로 돈다(handleSaveSchedule이 컴포저 값을 프로젝트에 먼저 기억한다). 종료 시각은 예약이 정한 값이라 다음 시작의 기본값으로 기억하지 않는다(launchRun의 remember). 예약 상태 문장은 viewFormat.js(describeSchedule·describeScheduleStatus·describeScheduleLast·describeScheduleSummary)가 만든다.
- 사용량은 대상 프로젝트가 고른 계정의 claudeAccount 조회값을 쓴다. 조회가 안 되는 환경(로그인 정보를 읽지 못하는 경우)에서는 한도 리셋 예약이 판단하지 못한다는 안내를 보이고, 정해진 시각 예약은 그대로 동작한다.
- tests/checkDesktopSchedule.js가 규칙·스케줄러를, tests/checkDesktopView.js가 상태 문장을 검증한다.

## React 화면(desktop/ui)

- 화면 전체를 React 19가 그린다. index.html은 `<div id="root">` 하나와 서체 선언(fonts/pretendard.css)·번들(bundle/app.js·app.css)만 불러오고, 소스는 desktop/ui/(ESM·JSX)이며 esbuild(ui/build.mjs)가 desktop/bundle/로 묶는다(npm run build:ui, 저장할 때마다 다시 만들려면 npm run dev:ui). 번들은 커밋하지 않고 패키지에는 번들만 넣는다. 번들이 없으면 스모크 테스트가 #run-form을 못 찾아 실패한다. react·react-dom·esbuild·zustand·marked(마크다운 토큰화. 글만 나누고 HTML로 바꾸지 않는다)는 devDependency이고 exact로 고정한다(올릴 때는 최근 2주 안에 나온 버전을 피한다).
- 구성
    - main.jsx는 메인이 보관한 첫 상태를 모두 받은 뒤(boot.js) App.jsx를 그린다. boot.js는 첫 상태 적재, 메인 이벤트 구독, 실행 상태가 바뀔 때 다른 스토어가 따라야 하는 규칙(옛 renderState가 한꺼번에 하던 일)을 맡는다.
    - stores/는 zustand 스토어다. runStore(엔진 상태와 로그 3000줄. 로그는 50ms 단위로 모아 반영하고 shareStructure로 바뀌지 않은 조각의 참조를 유지한다), appStore(앱 정보·저장된 설정·창), uiStore(패널·시트 전환 규칙·안내·시작 중 잠금), modalStore(확인 모달 요청), composerStore(모델·Effort·정책·종료 시각·작업·한도 연장, 실행 중 엔진 값 따라가기, 옵션 전달 큐), accountStore, scheduleStore, runsStore, tabsStore(열린 탭과 각 탭의 실행 상태·보는 탭), clock(초 단위 틱 하나를 모두가 나눠 쓰고 useClock은 읽은 값이 바뀔 때만 다시 그린다)이다.
    - actions/는 IPC를 부르는 일(run·runs·accounts·schedules·tabs)과 메인 이벤트를 반영하는 일(events)이다. 보는 프로젝트가 바뀌는 모든 길(프로젝트 고르기·탭 열기·전환·닫기)은 actions/tabs의 applyProjectSwitch가 받는다. 보는 프로젝트가 바뀌면 컴포저를 그 프로젝트의 저장된 값으로 채우고 상태·로그를 응답의 스냅샷으로 바꾸며(이야기도 resetLogs로 다시 짠다), 떠난 탭에서 저장하지 않은 컴포저 값(저장된 값과 다른 키만, 실행 중이던 탭은 제외)은 기억해 두었다가 돌아오면 저장된 값 위에 얹는다. 보는 프로젝트가 그대로면(다른 탭을 닫았을 때) 탭 목록과 설정만 바꾸고 컴포저·이야기는 건드리지 않는다. 컴포넌트는 window.autopilot을 직접 부르지 않고 액션을 부른다.
    - features/는 화면 단위(shell·ready·run·done·composer·profile·settings·history·archive·schedule)다. shell의 Rail(스토어를 읽는 껍데기)과 ProjectList(받은 탭 목록과 보는 프로젝트의 상태 줄을 그린다. 서버 렌더에서 zustand는 초기 상태만 읽으므로 마크업 검증은 ProjectList로 한다)가 레일의 프로젝트 목록을 그리고, TitleBar가 실행 줄을 그린다. 각 화면은 스토어를 선택자 단위로 구독하고, 객체를 고를 때는 useShallow를 쓴다.
    - components/는 공통 컴포넌트다(Icon·Button·Chip·Tag·SwapText·Popover·Select·Panel·Scrim·Modal·ModalHost·SettingsGroup·Gains·RunList·Symbols·ProviderAvatar·AvatarRing). 그 컴포넌트에만 쓰는 CSS(Select.css·Modal.css)는 같은 이름의 .css로 옆에 두고, 토큰은 styles/base.css의 :root를 쓴다.
    - hooks/(useReplay·useWidthTween·useMergedRef·useView·useBodyFlags·useOverlayDismiss·useAnyRunning), lib/(constants: 허용 값·MAIN_ACTIONS, shareStructure, runText, cx)가 받친다. 허용 값(constants.js)은 엔진 config.js·autopilotRunner.cjs와 함께 바꾸고 tests/checkDesktopRunner.js가 대조한다.
- CSS가 body의 data-view·data-status·data-tasks-open·클래스(ready·*-open)에 기대므로 useBodyFlags가 화면 상태를 그 한 곳에 반영한다. #root는 display: contents라 body의 flex 배치에 끼지 않는다.
- 공통 스타일은 ui/styles/의 영역별 파일이다(base 토큰·기본, shell 헤더·상태 줄, stage 본문 세 화면, controls 안내·버튼, composer 컴포저·팝오버, panels 스크림·설정·프로필, sheets 전체 기록·지난 실행, responsive, motion, schedule 예약 시트). index.css의 @import 순서가 곧 캐스케이드라 바꾸지 않는다. main.jsx가 index.css를 맨 먼저 불러 컴포넌트 전용 CSS보다 앞에 놓이고, esbuild가 bundle/app.css 하나로 묶는다.
- 성능: 구독은 선택자 단위이고, 이벤트마다 새로 오는 상태 객체는 shareStructure로 바뀐 조각만 새 참조가 된다. 시계는 하나다. 로그 줄은 늘어나기만 하는 불변 객체라 새 줄만 DOM에 더해지고, 전체 기록은 열려 있을 때만 그린다(가상화는 전체 선택·복사를 깨므로 쓰지 않는다). 지난 실행 상세의 대화 변환은 기록당 한 번(useMemo)이다. 팝오버·패널은 native popover·inert·CSS 전환을 쓴다.
- 애니메이션: 이야기(features/run/RunView)는 렌더 직전에 위치를 재고(measureTops) flushSync로 커밋한 뒤 layout effect에서 FLIP(slidePast)을 걸고, 드러내기 마스크(reveal.js)와 애니메이션 대기 게이트(busy·dirty와 Promise.allSettled)로 끝나기 전에 온 상태를 모았다가 한 번 그린다. 문구가 바뀔 때 맺히는 전환(SwapText, 정책 이름의 tick-up)과 알약 너비 전환(useWidthTween. 출발 너비는 ResizeObserver가 기억한 바뀌기 직전의 실제 너비다)은 훅이 한다. 애니메이션 클래스를 다시 거는 요소의 className prop에는 그 클래스를 넣지 않는다(React가 다시 쓰지 않아 클래스가 남는다).
- Select는 설정 패널의 옛 선택 상자를 개선한 것이고 새 선택 UI의 기준이다(높이 32·반경 8·안쪽 1px 테두리. inline이면 문장 속에 끼는 알약 모양이다). 목록은 트리거보다 좁아지지 않고 항목 이름·설명이 길면 넓어지다 상한(360px)에서 줄을 바꾼다(잘라 내지 않는다). 목록은 native popover(auto)와 anchor 위치라 패널 스크롤 안에서도 잘리지 않고, 트리거 아래에 붙다가 자리가 모자라면 위로 뒤집힌다. 항목은 이름 아래에 설명을 두고(알약 팝오버와 같은 흰 카드·모션) 고른 항목은 배경과 체크로 보인다(파랑은 쓰지 않는다). 키보드는 select-only combobox를 따라 트리거에 포커스가 남고(↑↓·Home·End·PageUp/Down·글자 이어 치기·Enter/Space로 고름·Esc로 닫음) 실행 중에는 알약처럼 회색 + 자물쇠로 잠긴다.
- 팝오버가 열린 동안은 useOverlayDismiss가 Esc를 처리하지 않는다. 안 그러면 선택 목록을 닫는 Esc가 설정 패널까지 닫는다. React 19에서 inert·popoverTarget·form이 속성대로 동작한다(18에서는 inert={true}가 빠진다).
- Modal은 GitHub Desktop 대화상자의 구성(제목 줄·본문·오른쪽 정렬 버튼 줄, 크게 맺혔다 빠르게 사라지는 전환)을 이 앱의 흰 카드 톤으로 옮긴 것이다. 네이티브 `<dialog>`를 showModal()로 열어 포커스 가두기·뒤쪽 비활성·Esc·닫힌 뒤 포커스 복원을 브라우저에 맡기고, 닫는 전환(display·overlay allow-discrete)이 보이도록 항상 그려 두고 open으로만 연다. 코드가 닫아서 생긴 close 이벤트는 건너뛴다(isClosingRef). 안 그러면 연달아 연 새 모달을 지난 이벤트가 닫는다. 바깥(::backdrop) 닫기는 누르기와 떼기가 모두 바깥일 때만이다. 닫는 전환 동안은 [open]이 빠져 display만 flex로 남으므로 flex-direction 같은 레이아웃은 `.modal` 기본 규칙에 둔다(`[open]`에만 두면 닫히는 100ms 동안 row로 풀려 상자가 늘어난다. tests/checkDesktopUi.js가 확인). 그동안 상자와 배경은 pointer-events: none이다.
    - 호출은 `await modal.confirm({ title, message, confirmLabel, cancelLabel, tone })`(stores/modalStore.js)이고 확인이면 true, 취소·Esc·X·바깥 클릭이면 false로 풀린다. App의 ModalHost가 하나만 그리고, 떠 있을 때 다시 부르면 앞의 것은 false로 닫힌다. tone: "danger"는 확인 버튼이 붉고 취소에 먼저 포커스를 둔다(되돌릴 수 없는 일의 기본 선택은 안전한 쪽).
    - 모달이 떠 있는 동안은 useOverlayDismiss가 Esc와 바깥 누름을 처리하지 않는다. 안 그러면 모달 안의 누름·Esc가 뒤의 패널까지 닫는다. 움직임 줄이기에서는 확대만 끄고 투명도 전환은 남긴다(schedule.css의 전역 규칙에서 .modal을 뺐다).
- 검증: tests/checkDesktopUi.js(키 이동 함수·Select·Modal 마크업), tests/checkDesktopStores.js(구조 공유, 로그 묶음·번호, 패널 전환, 확인 모달 요청, 옵션 전달 큐, 시작 중복 방지, 종료 신호 확인, 로그인 뒤 시작 이어가기, 예약 저장), 스모크(마운트와 주요 자리 확인)가 있다. 화면 모양과 동작은 tests/tools/ui의 비교 도구로 확인한다. 가짜 preload(fakePreload.cjs)로 두 화면을 같은 장면(scenes/)으로 띄워 진짜 마우스·키보드 입력을 보내고 영역별 PNG·정규화한 DOM·IPC 호출을 비교한다(`npm run ui:parity -- --baseline <git ref> [--full]`. 기준은 그 ref의 desktop·docs이고 화면 번들까지 만들어 쓴다). 화면을 고칠 때는 고치기 전 커밋을 기준으로 의도한 차이만 남는지 확인하고 장면을 더한다. 확인 대기는 주황이 숨 쉬고, 이어서 할 단계는 점선이다. 아직 하지 않은 단계는 이름만, 좁은 창(960px 이하)에서는 마친 단계도 이름만 보인다. settings를 주면 막대 아래에 단계별 설정 묶음(.step-group)이 한 줄에 이어지고 넘치면 줄바꿈한다)이고 실행 화면도 settings 없이 같은 컴포넌트를 쓴다. 단계는 다섯(기획·디자인·개발·테스트/QA·보안검토)이고, 문장의 선택지와 말은 buildSteps(BRAINSTORM_OPTIONS·GATE_OPTIONS·ON_FAIL_WHEN·MAX_ON_FAIL_RETRIES)가 정한다. 개발은 정할 것이 없어 설정 묶음이 없다. 칸 설명이 잘리면 title로 전체를 보여준다. 칸 상태·안내 문장·주 버튼 글자는 ui/lib/buildSteps.js(getReadySteps·getBuildGreeting·getBuildActionLabel·getBuildStartPhase, 확인을 기다리던 단계는 승인 없이 시작하면 다시 하므로 그 칸이 hold이고 버튼은 `<단계> 다시 하기`)가 정하고 tests/checkDesktopUi.js가 검증한다. 설정 묶음은 선택에 따라 바뀌는 한 줄 문장이고(예: `기획은 [Claude만 써서] 진행하고, 끝나면 [멈추고 확인 받을게요].`) 문장 속 선택은 알약 모양 Select(inline)다. 기획·디자인은 누가 쓸지(brainstorm·debate)와 끝난 뒤 멈출지(gates)를, 디자인은 산출물 형식(figma·image인데 send를 허용하지 않으면 HTML로 만든다는 안내)을, 테스트/QA·보안검토는 실패하면 개발로 몇 번까지 되돌릴지를 숫자 조절기(components/Stepper: 알약 안에서 − 3 + 로 줄이고 늘림, role=spinbutton이라 ↑→↓←·Home·End로도 바꿈)로 정한다(`개발로 [− 3 +]번까지 되돌려 다시 고쳐요`, 범위 0~5이고 0이면 `번 되돌려요. 되돌리지 않고 결과만 남기고 멈춰요.`). 저장 값은 그대로 stop·retry:N이고 buildSteps의 getMaxRetries·toOnFailValue가 횟수와 오간다. 마친 단계는 펼치지 않는다. 문장 속 선택의 목록은 설명이 잘리지 않게 트리거보다 넓게(최소 248px) 열리고 설명은 줄을 바꾼다. run(.story)은 ProjectHead와 상태 알약(components/HeadTag: tone run은 accent 바탕과 도는 고리, ok·warn·danger·muted는 결과 색과 아이콘. 신규 개발은 `신규 개발, <단계> 중`, 유지 보수는 `유지 보수, <정책>`, 종료 신호 뒤에는 warn), 신규 개발이면 한 줄 단계 카드(#run-steps, buildSteps.getRunSteps: 엔진 [단계] 줄의 runner state.step이 지금 단계이고 오기 전에는 시작할 단계, 지난 단계 중 확인받기로 둔 것은 확인함, 테스트/QA에서 돌아온 개발은 `다시 개발 N/M`), 그 아래 .run-grid(왼쪽 .run-main에 상태 줄과 이야기, 오른쪽 #run-card: 신규 개발은 단계 문서(buildSteps.getPhaseDocs, 누르면 openPhaseDoc), 유지 보수는 회차 목록, 남은 칸에 남긴 커밋과 Work 숫자)다. 1000px보다 좁으면 카드는 이야기 아래의 숫자 한 줄로 줄어든다. done은 실행을 마친 뒤의 정리(.finish: ProjectHead와 결과 알약(viewFormat.getPastStatus), 신규 개발 단계 카드, 상태 줄, 왼쪽에 인사·성과·버튼, 오른쪽 카드에 회차별 커밋)로, 실행이 끝난 상태가 남아 있는 동안 보이고 다른 프로젝트를 고르면 ready로 돌아간다(isFinishDismissed). 신규 개발을 모두 마쳤으면 `유지 보수로 이어 다듬기`(모드를 바꾸고 시작 화면으로), 테스트/QA 실패면 `qa.md 열기`를 더한다.
- 확인 기다림(features/approval/ApprovalView, hooks/useApproval): runsStore.buildPhase.awaiting이 있으면 신규 개발 모드의 시작 전, 그리고 `<단계> 확인 대기`로 끝난 실행의 마친 화면이 이 화면이다(body[data-approval]: 컴포저는 알약만 남기고 작업 칸·주 버튼을 숨긴다). 경고 알약, hold 칸의 단계 카드, 산출물 미리보기(DocPreview: components/Markdown이 marked로 글을 토큰으로만 나눠(lexMarkdown) 제목·문단·중첩/번호/체크 목록·표·인용·코드·구분선·굵게·기울임·취소선을 React 요소로 그린다. HTML·링크는 해석하지 않고 글자로 남아 눌러서 열리지 않는다. 제목이 같은 단계로 둘 이상이면 그 제목마다 접고 펴는 칸(.doc-section)과 `모두 접기`를 두고, 칸 안에서 스크롤한다. 디자인 폴더는 파일 목록), 오른쪽 카드에 `확인하고 <다음 단계> 시작`(approveAndStart: approve 뒤 지금 컴포저 값으로 시작), 산출물 전체 열기(openPhaseDoc), 고칠 점 칸과 `이 내용으로 <단계> 다시 하기`(revisePhase: 승인 없이 시작하며 작업은 buildSteps.getRevisionTasks로 수정 요청과 처음 적은 만들 것을 합치고 keepTasks로 작업 칸의 만들 것을 기본값으로 남긴다), 방금 실행이면 회차·시간·커밋 수와 작업 브랜치를 둔다. 좁은 창에서는 미리보기 아래로 카드가 내려가고 이 화면만 본문 안에서 스크롤한다. buildPhase.proposals가 그 단계의 후보(둘 이상)이고 아직 고르지 않았으면 같은 자리를 approval/ProposalCompare가 대신한다: 후보마다 열(머리에 이름 · 열기 · `이 안으로 <다음 단계> 시작` #approval-pick-<제공자> → approveAndStart(제공자)), 미리보기(후보의 맨 앞인 메인의 안은 단계 산출물, 보조의 안은 `<단계>-<제공자>` 문서(ProposalCompare의 getDocKey). HTML 안은 그리지 않고 열기로 안내), 상대의 검토(접힘)를 두고, 고칠 점은 아래 접힌 `둘 다 아쉬우면` 칸이 맡는다. 문서는 approval/usePhaseDoc이 읽는다. 시작 전 단계 카드(ready/BuildReady)의 각 단계 칸은 선택에 따라 문장이 바뀌는 글이다. 모든 단계가 메인 선택(Claude가 메인 · Codex가 메인, buildSteps.getMainOptions, Codex를 쓸 수 없으면 이유와 함께 잠금)을 갖고, 기획 · 디자인은 이어서 보조(buildSteps.getAssistOptions: 보조 없이 · 메인의 반대쪽 AI가 따로 안을 내서 · 협의해서. Codex 보조는 Codex를 쓸 수 없으면 잠기고 Claude 보조는 잠기지 않는다)를 고른다. 보조가 있는 단계는 고르려고 늘 멈추므로 끝난 뒤 선택 대신 `끝나면 멈추고 …고를게요`로 고정해 쓴다. 테스트/QA·보안검토는 메인과 되돌리는 횟수(Stepper, 0이면 되돌리지 않고 멈춤)를 문장에 둔다. 협의 횟수(Stepper, 1~20)·교차검토는 보조를 쓰는 단계가 모두 같은 값을 쓰므로 단계 줄이 아니라 기획·디자인 줄 뒤의 `보조` 공통 줄(StepCard의 extra, AssistSettings)에 한 번만 두고, 보조를 쓰는 단계가 있을 때만 보인다(협의 횟수는 협의 단계가, 교차검토는 나란히 비교하는 단계가 있을 때만). 모델과 노력·추론은 이 문장이 아니라 입력창의 AI 알약이 맡는다.
- 이야기는 storyModel(features/run)이 로그 묶음마다 viewFormat.applyStoryEntry로 Claude의 문장(시각 + 본문 줄, 여러 줄 메시지의 4칸 들여 쓴 줄은 앞 문장에 잇는다)과 도구 줄(`HH:MM:SS   > 이름 인자`)을 묶음(beat)으로 만든다. 앱이 엔진을 시작·연결하는 [앱] 줄이 오면 이야기를 비운다.

## 컴포저와 패널

- 실행이 시작되면 컴포저가 아래에 붙은 얇은 막대로 줄어든다(position: sticky, 좌우 여백은 그대로 두고 흰 바탕·그림자로 떠 있게 한다). 작업 칸(textarea, 높이 고정, 넘치면 칸 안에서 스크롤)은 접혀 작업 요약 한 줄 #tasks-toggle만 남고, 누르면 .fold의 grid-template-rows 0fr↔1fr 전환으로 읽기 전용 작업 칸이 펴진다. 접힌 칸은 visibility로 포커스를 막고 실행이 끝나면 접힌 상태로 돌아간다. uiStore의 tasksOpen을 useBodyFlags가 body[data-tasks-open]에 반영한다.
- 주 버튼(#main-action, 글자 #main-action-label)은 시작 → 종료 신호 → 종료로 바뀐다. 종료 신호는 실수 방지로 한 번 누르면 붉게 바뀌어 4초 동안 "한 번 더 눌러 종료"를 보이고(줄어드는 채움이 남은 시간을 알린다) 그 안에 다시 눌러야 stop을 보낸다(actions/run.js의 setStopArmed). 시작은 응답을 기다리는 동안 다시 누르지 못하게 잠근다(uiStore의 isStarting). 종료는 강제 종료이며 화면의 확인 모달(actions/run.js)을 거친다.
- 알약 줄(.composer-bar)은 Claude(#ai-pill-claude)·Codex(#ai-pill-codex) AI 알약(모델과 노력·추론을 하나로 묶음, 위 실행 에이전트 항목)·개선 정책(#policy-popover, 유지 보수) 또는 허용(#allow-popover, 신규 개발: ALLOW_KEYS 네 항목(위험도 낮은 순)마다 세 칸 위험도 막대와 이름, 고르면 위험도 색으로 채워짐, composer.toggleAllow. 가리킨 항목의 위험한 이유·허용해도 지키는 선·지금 설정이 그 허용에 기대는 곳은 아래 설명 칸에 보이고, 고른 것 중 가장 높은 위험도는 머리 줄과 알약 점에 알리며, 풀 수 없는 규칙(비밀값·운영 환경·Git 보호·파일 삭제)은 아래에 늘 둔다. 내용은 buildSteps의 ALLOW_OPTIONS·getAllowRisk·getAllowUsage이고 엔진 guideText의 ALLOWED_LINES와 뜻을 맞춘다)·종료 시각(#end-time-popover)이다. 노력(추론) 파형은 components/Wave가 path의 d를 정하고, 모델·노력·종료 시각 같은 선택 값은 composerStore가 갖는다.
- 종료 시각 값은 빈 값(07:00)·HH:mm(다음에 오는 그 시각)·"yyyy-MM-dd HH:mm"이고, 24시간 안이면 HH:mm으로, 그보다 뒤면 날짜를 붙여 둔다(viewFormat.toEndTimeValue. 엔진이 HH:mm을 다음에 오는 그 시각으로 읽어 같은 때를 가리킨다). 팝오버는 바로가기(3시간 뒤·내일 07:00·주말 내내=다음 월요일 07:00·일주일=상한), 오늘부터 MAX_RUN_DAYS(7)일 뒤까지 8칸 날짜 띠(이미 지나 닿을 수 없는 날은 잠김), 끝낼 시각 칸(직접 입력은 Enter·포커스를 떠날 때, ↑↓는 10분·Shift는 1시간), 남은 시간 합계다. 날짜와 시각은 따로 바뀐다: 시각을 옮겨도 고른 날은 그대로이고(shiftEndTime), 날을 고르면 시각은 그대로다(buildEndTime. 지난 시각은 다음 날로, 상한을 넘으면 상한 안의 5분 단위로 당긴다). 알약은 오늘·내일·날짜와 요일(formatEndTimeLabel)과 남은 시간, 안내 문장은 24시간 안이면 시각만·그보다 뒤면 요일(formatEndTimeShort)로 쓴다. 날짜가 붙은 값은 메인이 다음 기본값으로 기억하지 않는다.
- 신규 개발의 주 버튼은 다음에 할 단계 이름(`기획 시작`·`디자인 시작`, 확인을 기다리던 단계는 `<단계> 다시 하기`)이고, 기획인데 작업 칸(만들 것)이 비었거나 모든 단계를 마쳤으면 잠기고 이유를 title로 보인다. 작업 칸의 안내와 실행 중 요약(`만들 것`)도 모드를 따른다.
- 정책 값도 composerStore가 갖고 정책 팝오버의 버튼은 그 값만 바꾼다. 설정 패널의 "실행 기본값"(RunDefaults)이 모델·Effort·정책의 설정 범위별 기본을 정한다.
- 설정 패널의 "설정 범위"(ScopeGroup, uiStore의 settingsScope)는 패널에서 바꾸는 값을 전역과 이 프로젝트 중 어디에 저장할지 고른다. 프로젝트를 고르지 않았으면 이 프로젝트 범위는 막히고 전역으로 본다(actions/settings.getScope). 범위가 있는 줄(RunDefaults·모델 버전·사용량 한도 연장)은 이 프로젝트 범위에서 ScopeNote로 "전역 값을 따라가요" 또는 "이 프로젝트 값"과 되돌리기를 보이고, 되돌리기는 덮어쓴 값을 지운다(autopilot:reset-settings). 패널에서 바꾼 값은 바로 저장되고(autopilot:update-settings, 이 프로젝트 범위는 전역과 같아도 덮어쓴 값으로 고정) 컴포저는 바뀐 키만 따라가며(composer.loadSettings), 프로젝트를 바꾸면 컴포저를 새 프로젝트 값으로 다시 채운다. 실행 중에는 범위가 있는 줄을 잠그고 메인도 거부한다.
- 실행 중에는 정책·종료 시각 알약을 숨긴다(종료 시각과 남은 시간은 상태 줄·진행선에, 정책은 작업 요약의 문구에 이미 있다). 알약 줄은 줄바꿈 없이 한 줄에 들어가야 하므로 좁은 창(560px 이하)에서는 남은 시간과 화살표를 숨긴다.
- 팝오버는 native popover와 anchor 위치를 쓰고 컴포저가 아래에 있어 위로 열린다. display는 :popover-open에만 준다(닫힌 팝오버에 display를 주면 보이지 않는 목록이 남아 클릭으로 값이 바뀐다). 모델 라디오(name="model")는 팝오버 안에 있지만 form="run-form"으로 폼에 속하고, 마크·아이콘은 svg.symbols의 symbol을 use로 쓴다.
- 프로필 패널(#profile, #profile-toggle)과 설정 패널(#settings, #settings-toggle)은 레일 오른쪽에 뜨는 같은 .panel 컴포넌트이며(설정은 실행 줄 아래부터 세로로 길게, 프로필은 계정 카드 옆 아래쪽) 한 번에 하나만 열린다(uiStore의 setPanel·togglePanel). 설정 패널은 닫혀 있으면 inert이고 열 때 ease-out·닫을 때 ease-in이며, 뒤에 레일 오른쪽·실행 줄 아래만 덮는 .scrim을 깐다(레일은 덮지 않아 다른 메뉴로 바로 바꿀 수 있고, 실행 줄은 끌기 영역이라 배경색만 맞춘다). 시트(전체 기록·지난 실행·예약)도 레일 오른쪽에서 올라온다. 프로필 패널은 위에서부터 계정 카드(AvatarRing lg)·로그인 만료 안내(#login-expiry, 3일 안이거나 다시 로그인이 필요하면 주황 상자에 #account-login)·사용량·계정(알약 줄. #account-select 안에 AccountList가 role=radio 버튼으로 그리고 끝에 점선 #account-add)·푸터(기준 시각, 이 계정 제거, 새로 고침)다. 사용량 막대 위 세로 선(.usage-pace)은 한도 기간이 지난 만큼이고 쓴 비율이 15%p 넘게 앞서면 "시간보다 빨리 쓰고 있어요"를 더한다(viewFormat.getUsagePace. 이름이 "5시간"·"주간"으로 시작하는 한도만 기간을 안다. tests/checkDesktopView.js가 검증).
- 진행 기록 초기화(설정 패널)는 확인 모달을 거쳐 reset-progress를 실행하고 실행 중에는 막는다. 버튼은 공통 .button(primary·danger·small 조합)을 쓴다.

## 시각 규칙

- 화면은 "구름" 디자인 시스템이다(Paneloom과 같은 토큰 이름, styles/base.css :root). 옅은 하늘색 바탕(--page) 위에 흰 면(--bg)이 그림자로 뜬다. 페이지에 바로 놓인 카드(컴포저·패널·시트)는 헤어라인 대신 그림자(--shadow-1, 들리면 --shadow-2, 팝오버·패널·대화상자는 --shadow)로 띄우고 카드 안쪽 항목은 헤어라인을 쓴다. 파랑(--accent) 하나를 주요 동작(시작 버튼은 --glow)·진행 중인 것·포커스에만 쓰고, 강조색 글자·아이콘은 --accent-ink, 상태 바탕은 --ok-wash·--warn-wash를 쓴다. 모서리는 --r-sm 9·--r-md 11·--r-lg 14·--r-xl 18과 알약(999px)이다. 색은 토큰으로만 쓴다(모델 알약의 계열 색 --tone만 예외이고 바탕은 color-mix로 --bg에 섞는다). 잉크로 채운 단추의 글자는 #fff가 아니라 var(--bg)다(다크에서 뒤집힌다).
- 다크: 전역 환경설정 theme(system·light·dark, 기본 system, settingsStore의 THEME_CHOICES, 설정 패널 "시스템 > 화면 테마")을 메인이 nativeTheme.themeSource로 정한다(autopilotIpc.applyTheme, 앱을 켤 때와 환경설정이 바뀔 때). 화면은 base.css의 `@media (prefers-color-scheme: dark)` 한 곳에서 토큰만 바꾸므로 첫 화면부터 깜빡이지 않고, 창 바탕(getWindowBackground: --page와 같은 색)·스크롤 막대·입력 칸도 함께 따른다. tests/tools/ui의 runScenes는 `--theme dark`로 같은 방식으로 찍는다.
- 글자 크기는 styles/base.css :root의 열 단계(--text-xs 12 ~ --display 56)만 쓴다.
- 서체는 desktop/fonts/의 Pretendard(OFL, 라이선스 파일 동봉)를 fonts/pretendard.css의 @font-face로 넣어 오프라인에서도 같게 보이게 한다. 글꼴과 라이선스를 한 폴더에 두고 docs/mockups도 그 파일을 쓰므로 번들에 넣지 않고 index.html이 직접 불러온다. 숫자는 body의 tabular-nums(Pretendard 고정폭 숫자)로 써서 시계가 바뀌어도 흔들리지 않게 한다.
- 고정폭 서체(--mono, Windows의 Cascadia Mono)는 코드·경로·해시·전체 로그에만 쓴다(한글이 섞인 숫자 문구에 쓰면 글자 사이가 벌어진다).
- 지금 문장은 줄 순서대로 마스크를 쓸어 드러내고(features/run/reveal.js, 글자 위치는 그대로다), 드러내는 중에 문장이 이어지면 마스크를 걷어 다 보여준다. 길이에 따라 글자 크기를 줄이고(data-length) 12줄을 넘으면 말줄임 없이 문장 안에서 스크롤한다. 도구 칩은 말줄임이 있어 title에 전체 이름과 인자를 담는다.
- 이야기의 글 사이 간격(지난 문장끼리·마지막 지난 문장과 성과·성과와 지금 문장)은 `.story`의 `--story-gap` 하나다. 줄 높이가 글자 위아래에 더하는 여백은 글마다 달라 간격을 따로 쓰면 어긋나므로, 지난 문장(`.said`)은 위아래 `margin-block: calc((1em - 1lh) / 2)`로, 지금 문장(`.now`)은 위쪽에서 그 여백을 걷는다(글자 크기가 달라도 보이는 간격이 같다). 새 글을 이 줄 사이에 넣을 때도 padding·margin으로 간격을 더하지 말고 이 둘을 쓴다.
- prefers-reduced-motion에서는 이동·확대 전환(패널·시트·팝오버 미끄러짐, 등장)을 끄고, 자리가 바뀌지 않는 투명도 표시(캐럿 깜빡임, 상태 점, 문장 드러내기, 문구 전환)만 남긴다. 진행 중 고리(.ring)는 돌지 않고 꽉 찬 고리가 숨쉬듯 흐려졌다 밝아진다(shell.css).
- 창을 숨기면(document.hidden) :root.window-hidden으로 반복 애니메이션을 멈춘다. 등장 애니메이션은 서체가 준비돼 body.ready가 붙기 전까지 멈춰 둔다.

## 창과 시스템 연동

- 창은 가로형 1160×800(최소 760×620, 작업 영역보다 크면 줄인다. 960px보다 좁으면 레일이 아이콘 띠로 접힌다)이고 frame 없이 테마에 맞는 바탕(autopilotIpc.getWindowBackground, 화면의 --page와 같은 색)으로 첫 화면이 그려진 뒤(ready-to-show) 띄운다.
- 실행 줄(#titlebar)은 features/shell/TitleBar.jsx에서 직접 그린다. 오른쪽에 #update-chip과 최소화·최대화·닫기 버튼만 둔다. 프로젝트별 진행 상태는 레일이 알리므로 여기에는 두지 않는다. 줄 전체가 끌기 영역(-webkit-app-region: drag)이고 버튼만 뺀다. 프로필·설정·예약·지난 실행 버튼은 레일에 있다.
- 최소화·최대화·닫기는 preload의 window.appWindow가 main.cjs의 window:* IPC로 요청한 창에만 적용한다. 닫기는 일반 close라 실행 중 확인을 그대로 거친다. 최대화 상태는 window:state로 받아 아이콘을 바꾼다.
- 앱은 단일 인스턴스이며 두 번째 실행은 종료하고 기존 창을 앞으로 가져온다(--smoke-test는 실행 중인 앱과 무관하게 검증하도록 잠금에서 제외한다).
- 앱이 시작한 엔진이 실행 중이거나 설정의 "닫아도 트레이에서 계속 켜 두기"(settings.json의 keepInTray)가 켜져 있으면 창을 닫을 때 트레이로 숨기기만 한다(main.cjs의 close 처리, isOwnedEngineRunning·isTrayResident). 종료는 트레이 메뉴의 종료로 하며 창을 띄워 confirmClose의 확인 후 강제 종료한다. 그 밖에는(실행 중이 아니고 트레이 상주도 꺼져 있거나 연결한 엔진이면) 닫을 때 앱이 종료된다. 트레이에서 종료할 때는 window closed에서 app.quit()을 불러 macOS에서도 끝낸다.
- "로그인하면 자동으로 켜기"(launchAtLogin)는 launchAtLogin.cjs가 맡는다. Windows·macOS는 app.setLoginItemSettings(인자 `--hidden`. Windows 값 이름은 기본인 AppUserModelId로 둔다. getLoginItemSettings가 name을 받지 않아 다른 이름으로 쓰면 등록돼도 확인되지 않는다), Linux는 ~/.config/autostart/autopilot.desktop을 쓰고, 포터블 exe·AppImage는 원본 파일(PORTABLE_EXECUTABLE_FILE·APPIMAGE)을 가리킨다. 개발 실행(app.isPackaged가 거짓)에서는 등록하지 않는다. 켜면 keepInTray도 함께 켜고 화면에서 끌 수 없게 잠근다(handleSetSystem). 등록 뒤 시스템에서 다시 읽어 확인하고 실패하면 설정을 바꾸지 않는다. 앱을 켤 때 syncLaunchAtLogin이 경로를 다시 맞춘다. `--hidden`(macOS는 wasOpenedAtLogin)으로 켜지면 창을 띄우지 않고 트레이에만 둔다. NSIS 제거 때 로그인 항목은 build/installer.nsh가 지운다.
- systemIntegration.cjs가 러너 상태 변화(onState)마다 절전 방지(powerSaveBlocker prevent-app-suspension, 엔진이 도는 동안), 작업표시줄 진행률(종료 시각까지 경과, 종료 신호·재시도·한도 대기는 paused), 트레이 툴팁, 알림(종료·실패·사용량 한도 대기 전환과 예약 시작·실패, 강제 종료 제외)을 맞춘다. 끝난 뒤 PC 동작(postRunAction: none·sleep·shutdown, 기본 none)은 postAction.cjs가 맡는다. shouldRunPostAction은 앱이 시작한 실행(연결한 엔진 제외)이 스스로 끝났을 때만 참이고(강제 종료·중단 요청 제외), 참이면 autopilotIpc.watchPostAction이 창을 띄우고 createPostAction으로 POST_ACTION_DELAY_MS(1분) 동안 기다린다. 기다리는 상태({action, at})는 autopilot:post-action으로 화면의 안내 줄(#post-action-banner)에 보내고 취소(autopilot:cancel-post-action)·바로 실행(autopilot:run-post-action-now)을 받으며, 새 실행이 시작되면 취소한다. 실행은 셸 없이 execFile로 하는 getPowerCommand(Windows 절전은 SetSuspendState가 최대 절전으로 빠질 수 있어 WinForms Suspend, macOS pmset·osascript, Linux systemctl)다. 이 설정은 NON_PORTABLE_KEYS라 내보내기·가져오기에 담기지 않고 기본값 복원 때 none으로 돌아가며, 종료로 바꿀 때는 화면의 확인 모달을 거친다. 테스트는 실제로 절전·종료하지 않고 순수 함수와 타이머만 검증한다(tests/checkDesktopSystem.js). 절전 방지는 설정 sleepBlock(always·plugged·never)을 따르고(shouldBlockSleep), 상태가 바뀔 때마다 설정을 읽지 않도록 실행 중인지가 바뀔 때와 환경설정·전원 상태(powerMonitor on-ac·on-battery, 스모크 테스트 제외)가 바뀔 때만 다시 판단한다. 알림은 종류(finish·failure·limit·schedule)별로 설정(notifyFinish·notifyFailure·notifyLimit·notifySchedule)이 켜져 있어야 하고, 창에 포커스가 있으면 notifyFocused가 켜진 경우에만 보낸다(shouldNotify). 설정은 systemIntegration.configure로 넘긴 읽기 함수로 알림을 보내는 때에만 읽고, 이런 전역 환경설정은 autopilot:set-preferences(settingsStore의 PREFERENCE_KEYS만, 실행 중에도 가능)로 저장한다. 전환 판단은 순수 함수 getTransitionNotice이고 tests/checkDesktopSystem.js가 검증한다.
- 스모크 테스트(npm test)는 window.appWindow·#titlebar·#profile·#login-banner도 확인한다. 창은 show하지 않고(ready-to-show에서 건너뜀) 숨긴 채로 검증하며, 끝날 때 창이 보이면 실패다. 트레이 아이콘은 만들어 두므로 잠깐 보일 수 있다. 실제 앱 데이터 대신 빈 임시 userData로 시작하므로(main.cjs, 루트 CLAUDE.md) 활성 프로젝트는 늘 기본값인 유지 보수다.
