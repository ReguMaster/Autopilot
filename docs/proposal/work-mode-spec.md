## 4. 엔진

### 4.1 CLI (추가)

```sh
--mode maintain|build                 # 기본 maintain. build면 --policy는 무시
--gate plan,design                    # 승인받을 단계
--allow deps,large,external-api,send  # 허용 체크박스
--design-format md|html|figma|image
--qa-on-fail retry:<N>|stop
approve --project <p>                 # 하위 명령. 승인 대기 중인 단계를 승인
```

### 4.2 단계 상태

- 앱 데이터 폴더의 진행 기록 옆 `PHASE.json`: `{ "phase": "plan|design|build|qa|done", "awaiting": null|"plan"|"design", "qaRetries": N }`. 실행이 끝나도 남아서 다음 실행이 이어받는다.
- 세션은 단계 산출물을 commit한 뒤 `.autopilot/progress/<날짜>/PHASE_DONE`을 만든다. 엔진은 `TODO_COMPLETE`처럼 성공한 회차 뒤에만 인정한다.
- QA 단계는 결과를 `PHASE_DONE` 첫 줄에 `pass` 또는 `fail`로 적는다. fail이면 `--qa-on-fail`에 따라 build로 되돌리거나 종료한다.
- 단계가 끝나고 그 단계가 `--gate`에 있으면 `awaiting`을 기록하고 실행을 끝낸다(종료 이유 `기획 승인 대기`). 밤새 기다리지 않고, 승인하면 다음 실행에서 이어간다.
- `approve`는 `awaiting`을 지우고 다음 단계로 넘긴다. 승인하지 않고 그대로 시작하면 같은 단계를 다시 하고, 작업 입력칸의 내용을 수정 요청으로 넣는다.
- `reset-progress`는 `PHASE.json`도 지운다.

### 4.3 로그 줄 (앱 파서 세 곳과 검증을 함께 고친다)

```
[단계] 기획 시작
[단계] 기획 완료
[단계] 기획 승인 대기
[단계] QA 실패 - 개발로 되돌림 (1/3)
```

### 4.4 프롬프트

- 단계마다 단계 지침을 넣는다(무엇을 만들고 어디에 commit하며 언제 `PHASE_DONE`을 만드는지).
- `getAutopilotPolicy(commitPrefix, workBranch, allow)`가 허용 항목에 해당하는 줄을 바꾼다.

## 9. 프로젝트 생성 (2026-10-30 결정)

- 레일에 "새 프로젝트"를 더한다(프로젝트 열기와 별도). 생성은 언제나 신규 개발이다.
- 입력은 "쓰기"보다 "고르기"로 한다(빈 칸 8개짜리 첫 시안은 쓰기 힘들다는 피드백으로 바꿈).
    1. 한두 줄 적기: 무엇을 만들고 싶은지 한두 줄(예시 칩으로 채울 수 있음) + 어디서 쓰나요 칩(웹 · 모바일 앱 · 데스크톱 앱 · 서버/API · CLI · 아직 몰라요, 몰라도 됨) + 만들 상위 폴더.
    2. "초안 만들기": Claude(작은 `claude -p` 한 번, 도구·MCP 없이 JSON)가 이름 · 한 줄 요약 · 사용자 · 기능(넣을 것과 추천) · 하지 않을 것 · 추천 기술 스택과 이유를 채운다. 실패하면 빈 다듬기 화면으로 넘어가고 이유를 알린다. "직접 다 쓸게요"는 AI 없이 다듬기 화면으로 간다.
    3. 초안 다듬기: 칩을 눌러 넣고 빼고(회색은 추천), 짧게 더 입력. 기술 스택은 추천대로 / 나중에(기획에서) / 직접. 참고 링크는 접어 둔다. 오른쪽에 brief.md 미리보기.
- 화면 문구에 dependency를 쓰지 않고 "라이브러리"로 쓴다(예: 새 라이브러리 추가).
- 초안 범위는 준비 화면까지: 폴더 만들기 → `git init -b main` → 입력을 `docs/autopilot/brief.md`로 정리해 첫 커밋 → 신규 개발 모드의 새 탭으로 열고 만들 것을 채운 시작 전 화면으로 이동. 기획 시작은 사용자가 누른다. 기획 단계는 brief.md를 먼저 읽는다.
- Git 작성자(user.name · user.email)가 없으면 생성 화면에서 받아 그 저장소에만 설정한다.
- 시안: docs/mockups/redesign/course.html의 "새 프로젝트" 장면(오른쪽에 brief.md 초안 미리보기).

## 10. 여러 AI 브레인스토밍 (2026-10-30 결정, 구현 전)

- 넣는 곳: 기획 · 디자인 단계, 그리고 교차검토. 단계 칸마다 사용자가 "Claude만 / Claude + Codex"를 고르고, 둘 다면 "교차검토"(서로 상대 안의 빈자리 · 위험을 짧게 지적)를 켤 수 있다. 새 프로젝트 초안은 Claude만 쓴다.
- 방식: 합치지 않고 각자 낸 안을 나란히 보여 주고, 사용자가 가장 좋은 안을 고른다. 그래서 둘 다 고른 단계는 확인받기 설정과 상관없이 끝나면 멈춘다(`approve --pick claude|codex`). Codex 안을 고르면 다음 실행이 그 안을 plan.md(또는 디자인 산출물)로 확정해 commit하고 다른 안은 docs/autopilot/proposals/에 남긴다.
- 실행: Claude는 평소처럼 단계 산출물을 쓰고, 엔진이 Codex(`codex exec -s read-only`, 같은 단계 지시)에게 독립 안을 받아 docs/autopilot/proposals/<단계>-codex.*에 둔다. Codex를 쓰려면 "외부 서비스로 보내기" 허용이 필요하고(고르면 함께 켜고 알림), 미설치 · 미로그인 · 실패면 건너뛰고 Claude 안으로 진행한다(로그로 알림).
- 제공자: Codex(GPT) 먼저. 제공자 목록 구조로 만들어 Gemini 등을 나중에 더한다(이 PC에는 Gemini CLI가 없다).

- 협의 모드 추가(2026-10-30): 칸에서 "Claude만 / 나란히 비교 / 협의"를 고른다. 협의는 각자 첫 안을 쓴 뒤 엔진이 사회자가 되어 Claude(`claude -p --resume`, `--json-schema`)와 Codex(`codex exec resume`)가 최대 3번 주고받게 하고(동의 · 반대와 이유 · 바꾼 점 · 합의 여부), Claude가 합의안과 협의 기록 · 못 맞춘 쟁점을 정리한다. 사용자는 쟁점마다 Claude 쪽 · Codex 쪽을 고른다(`approve --resolve`). 실행 중에는 Claude · Codex 말풍선이 채팅처럼 실시간으로 보인다.
